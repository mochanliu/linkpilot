## 1. 现成方案的调研结论

约束（都是这套项目自己的硬约束，不是偏好）：控制器只有一个 `go:embed console.html`
（`admin.go:19`）、没有静态资源路由；lab 与私有化部署都不能依赖公网瓦片服务；许可只收
MIT/BSD/Apache/ISC；构建侧没有 node/npm（宿主 go 1.19 也编不了，全部在 lab-ctrl 里跑）。

| 方案 | 许可 | 实测体积（raw / gz） | 离线矢量底图 | 结论 |
|---|---|---|---|---|
| Leaflet 1.9.4 + `L.geoJSON` | BSD-2 | leaflet.js 144KB/41KB + css 14KB/3KB | 可以（不挂 TileLayer） | 能用，但要为它加一条资源路由，且连线只有直线，弧线要插件（Geodesic 是 GPL-3，排除） |
| MapLibre GL | BSD-3 | 1032KB/269KB，npm 解包 29MB/762 文件 | 可以，但要自带 style + 行星底图（.pmtiles 百 MB 级） | 离线代价最差，排除 |
| ECharts 6.1 `geo`+`lines` | Apache-2 | 1095KB/360KB，且 v6 不再内置 world.js | 可以 | 弧线/动效最省事，但为一个页面背 360KB gz |
| vis-network / Cytoscape | Apache/MIT | 638KB / 425KB | 无底图 | 不是地图，排除 |
| **d3-geo 预投影 + world-atlas 几何** | ISC + Natural Earth 公有领域 | **运行时 0 库**，底图数据 131KB | 是 | **选它** |

思科自己的做法是反证：vManage 的 Geography 窗口要求浏览器能访问 `*.openstreetmaps.org`
的在线瓦片，按 GPS 坐标打点，控制连接画细蓝线、数据连接画细绿线；Crosswork 同样是
"把设备/链路/隧道按 GPS 放到世界地图上" + 逻辑/地理切换。也就是说**行业常规正是我们不能用的那部分**，
所以底图必须自带。

### 为什么运行时不需要 d3

底图在**生成时**投影成固定 viewBox 的 SVG 路径，运行时只需要把"设备经纬度"投到同一个坐标系。
Natural Earth I 的正向公式是 6 项多项式，12 行 JS。已实测：与 d3-geo `geoNaturalEarth1`
（scale 368.5459 / translate 1000,594.741）在北京、上海、伦敦、纽约、新加坡、悉尼、圣保罗、
雷克雅未克、开普敦上的输出**误差 0.000000px**。

生成物（`controller/tools/world-basemap/gen.mjs` 可重跑，源数据 world-atlas@2 的 `land-110m` + `countries-110m`，
纬度裁剪 [-60°,90°]，去掉南极洲后省 12%）：

```
land 55,798B + borders 55,822B + graticule 19,664B = 文件 131,620B（gzip 53KB）
```

一个坑记在这里：`d3.geoClipRectangle` 的参数是**弧度**。第一次按度传 (-180,-60,180,85) 时裁剪
静默无效（南极洲照画），改成弧度才生效——字节数和 translate 同时变了才算验证过。

## 2. 必须先补的数据：设备位置

模型里**没有任何经纬度**：node 只有 serial / 状态 / 中转端口 / VPN 端口 / 隧道数 / 接口清单，
tunnel 只有两端与路径。地图要按位置放点，就得新增字段。按"控制台不造数据"，缺位置的设备
不能猜一个点画上去——原型里的处理是：不进图，进右下角"未定位设备"清单，位置一栏写"未上报"。

两个候选（C 只允许城市预设已排除：客户站点不可能都在大城市）：

- **A 设备级 `location{lon,lat,label}`**：经纬度直接挂在设备行上，租户在「设备」页每台各填一次，
  填的时候给一个常用城市下拉帮你取值，存的是当时的经纬度快照。不引入新实体、不动 state 结构里的
  别的表，旧数据没值就是"未上报"。
  **代价**：同一个机房里的 3–5 台盒子（主 / 备 / 只做中转）要把同一串数字敲 3–5 遍；机房搬迁或者
  打错一位小数，要逐台改，而且没有任何机制阻止同址设备各写各的坐标——图上就会出现"同一栋楼里
  三台设备隔了 200 公里"。设备数量小的时候无所谓，上千台的时候这是运维成本。

- **B 站点（site）实体 + 设备引用**：新增一张 `site{id, name, lon, lat, tenant_id}` 表，设备行只存
  `site_id`。坐标属于站点，设备只是"站在站点里"：一个机房录一次，同址设备共享，改一次全站生效；
  地图要按位置聚合（同城多点合成一个可双击展开的簇）时，聚合的单位天然就是站点，而不是"坐标刚好
  相等的设备"。站点这一层以后还能挂地址文本、负责人、时区——都是现在没有、以后大概率要的东西。
  **代价**：第 1 步后端要多一张表 + 站点的增删改查接口 + 设备页位置控件从"两个输入框"变成
  "选站点 / 就地新建站点"；设备必须先有站点才能定位（但没站点照样只是"未上报"，不会坏数据）。
  隔离沿用现成的租户边界：站点归租户所有，运营方看得到归属但和现在一样不碰租户网络配置。

**他在 D3 里给出的规模（预期上千台 CPE）正是 B 划算的那个条件**，所以我现在把推荐从 A 改成 B；
上一条"建议 A"是在只看到 lab 里 4 台设备的前提下写的。如果他更看重这一版落地快，A 也能把图画出来，
将来再抽站点——迁移路径是干净的：把设备上的 `lon/lat` 按相同坐标归并成站点、写回 `site_id` 即可。

位置**不进配置包**（`/v1/underlay/bundle` 不变）：设备侧不需要它，加进去只会污染已定稿的契约（D2 已确认）。
校验：lon ∈ [-180,180]、lat ∈ [-90,90]，空值=未上报。

## 3. 拓扑页的交互（原型已实现的部分）

- **缩放平移**：滚轮以光标为锚点缩放（1×–14×）、拖拽平移、双击放大、`+ −` / 适应设备 / 全图按钮
  （按钮是原生 button，键盘可达；不给 SVG 加 tabindex）。
- **信息密度随缩放走**，线宽/字号按 `1/k` 反算，所以任何倍率下墨迹粗细恒定：
  - 缩略：海岸线 + 设备点；站名**按放得下才画**（贪心碰撞剔除），不是等某个倍率才出现。
  - 站点：连线上标隧道号。
  - 明细（≥4.5×）：连线标 `tN · 本端端口→对端端口`，设备下沿标 `序列号 · node-N · 中转端口`。
- **经中转的 SR 路径画成经过中转设备位置的虚线曲线**，直连是实线——这是这张图唯一比列表多出来的信息。
- **地理 / 逻辑双视图**（照 Crosswork 的开关）：lab 里设备都在同一台 Docker 主机上，地理视图会挤成一个点，
  逻辑视图（现有环形布局）才是能用的那张。原型里逻辑视图固定用"站点"密度，未定位设备也照样出现。
- 点击设备/连线 → 详情面板（字段与 `/api/underlay/topology` 的读模型一一对应，未上报的写"未上报"）。

## 8. 这一轮"在浏览器里点过"是怎么点的

截图工具在这个 webview 里拿不到视口（`visibilityState=hidden`），所以地图的像素证据是两条一起给的：

- **无头复跑同一段绘制代码**：把 `console.html` 里 `MAP` 到 `undMapAttach` 之间的那段源码原样切出来，
  配一个 DOM 桩在 node 里跑，输出 `svg` 文件。跑的是发布出去的同一份源码，不是重写的原型。
  `undMapFit` 的 k/x/y 与真实页面上的值逐位相同（2.9727 / −3832.786 / −644.844）。
- **真实页面的 DOM 探针**：`/assets/world-50m.js` 只在越过 4.5× 后被请求一次；请求前后 land 路径的
  `d` 长度从 19,664 变成 680,914；站点列、下拉选中值、提示文案、未定位清单都从 `#content` 里读实际渲染结果。

设备页站点交互的验证走的是真实浏览器：放置/清位/就地新建并放置/编辑改名改坐标/删除空站点/
删除带设备的站点被 409 拒绝并原文回显，以及"表单填到一半轮询不会冲掉"（13 秒后字段值与焦点仍在，
同期心跳的「x 秒前」照常老化）。

## 9. 风格对齐这一提交里，我偏离第 4 节那张表的三处

这三处都是我自己的取舍，不是他说的，写在这里供他否决——回退的成本很低，因为只有 `<style>` 块。

- **状态标签的类名没改**（`online/stale/pending/revoked/plan` 保持原名，没换成原型的
  `ok/warn/bad/off`）。改名要动十几处 JS 模板，视觉效果一位都不差，纯粹是 churn。
- **`.tag.*` 的描边沿用现有的浅色值**（`#aceebb / #eed888 / #ffcecb`），只把底色换成 token。
  三份原型在这件事上互相矛盾：`srou-console.html` 是 `border-color:transparent`，
  `topology-map-proto.html` 是浅描边 + `var(--ok-bg)`，`config-basic-proto.html` 是满色描边
  `border-color:var(--ok)`。他抱怨的是"拓扑图等监控界面"，拓扑那份是最近的参照，而且满色描边会让
  设备/监控页每一行状态 pill 都变成实心绿/红圈，比现在离"回归原样"更远。
  如果他更想要 config 原型那种更硬的描边，改的是这 5 行。
- **按钮与输入框的 `min-height:32px` 没引入**。第 4 节那张表里没有这一行，引入会改动表单控件的
  垂直节奏（现在是 padding 撑出来的高度），属于另一件事。

一处**照做了但表里没写**：`.cfg-note` 换成了原型的"3px 状态色左竖条 + 浅色底"
（`border-left:3px solid var(--accent|warn|bad)`），因为原来整圈同色描边的写法在原型里已经不存在了。

2026-10-29 他确认：这三处偏离连同上面那条照做的，**按现状保留，不回改**。

## 10. 第 6 步规模预演的实测结果（2026-10-29，`louis-gui` 登录 lab 控制台真实页面）

### 怎么量的（先把证据边界说清）

- **页面代码一行没改**。发生器 `window.__gen118(N)` / `__mock118(N)` 只注入在这个标签页的内存里
  （脚本已入库：`controller/tools/topo-scale-mock/mock118.js`，注入与复跑姿势见同目录 `README.md`；
  它喂的是内存里的文档，不进控制器、不进仓库数据），它只替换 `window.fetch` 对
  `/api/underlay/topology` 这一个路径的响应，其它请求照走真实控制器。真实页面的
  `ensureTopo → loadTopo → render → undMapAttach → undMapDraw` 全程跑的是发布出去的那份源码。
- **帧延迟** = 同步 `svg.dispatchEvent(new WheelEvent('wheel',{deltaY…}))` 前后的
  `performance.now()` 差，也就是 `undMapZoomTo → undMapDraw` 的一次完整重绘（建字符串 +
  `svg.innerHTML` 解析建树）。滚轮与拖动走的是同一个重绘函数，所以这个数字同时代表缩放和拖图。
  **它不含浏览器 paint**：这个 webview 的 `visibilityState=hidden`，拿不到视口（第 8 节那条老限制），
  所以下面所有毫秒数都是**下界**，他屏幕上真实感受到的卡顿只会更重。
- **这台机器不是中位客户机**：量的是他这台 Mac 上的这个 webview。但要看的东西不是绝对毫秒，是斜率
  （首屏 25 → 92 ms、明细档 57 → 202 ms/帧），斜率在更弱的机器上只会更陡不会更缓。
- **首屏** = `#nav a[data-view="underlay-topology"].click()` 这一次同步调用的耗时，
  包含整页 HTML（面板 + 站点表 + 未定位清单）与地图重绘。
- 每一档的数字都从页面自身读回（`#tp-zoom`、`#tp-level`、`.usage`、`querySelectorAll`），不是推算。
- 发生器 300/1000 用同一个种子（mulberry32, 20261029）、52 个真实城市坐标、站内 jitter ±0.01°、
  形态按 1000 台那份文档实测出来的比例：online 906 / stale 45 / pending 49、未定位 48、
  symmetric_nat 80、站点 454 个单台 + 57 个两台 + 42 个三台 + 44 个四台以上、
  1,424 组隧道里 183 组走中转（12.9%）、8 组路径模板已失效（0.6%）、239 组 `state≠up`（16.8%）。
  连接形态是 hub-spoke 全量 + 约三成挂第二个 hub + N/6 条随机 spoke-spoke。
  **第一版发生器自己有 bug**：同城第二台之后的设备拿不到 `site_id`，于是 300 台里有 101 台显示成
  未定位、站点台数虚高。加完自检（placed 数 == 各站点 `devices` 之和 == 无悬空引用）后修掉，
  下面的数字全部是修完之后重跑的。自检输出：300 台 → placed 286 / sum 286 / dangling 0；
  1000 台 → placed 952 / sum 952 / dangling 0。

### 四条结论

1. **每帧成本只跟"一共有多少台"有关，跟"看见多少"无关**。14× 时可见世界框是 143×74 单位
   （画幅的 1/14），实测 952 台里只有 **25 台**在框内（3%），可每一帧仍然把 952 个设备、
   1,388 条连线、3,292 个标签全部重建。所以撑不住的原因不是"设备多"，是**没有视口裁剪**。
2. **50m 底图不是瓶颈**（这条把 D3 里那个隐含担心直接消掉）。同一档（明细 lv2、300 台）在海岸线
   `d` 从 19,664 字符换成 680,914 字符前后，帧延迟 p50 56.6 ms → 56.4 ms（max 78.5 → 67.5），量不出差别。
   代价在设备与连线的墨迹上，不在海岸线上。
3. **标签在缩略档不是"糊"，是"根本没地方放"**。碰撞框是 58×16 世界单位（画幅 2000×1040），
   而同城设备在 k=1 下彼此只差约 0.1 个单位，所以**一个城市团最多只能落下一个名字**：
   实测 300 台 41 个 text、1000 台 42 个，**上限只跟城市团数有关，跟台数无关**。
   同一规模下更要紧的另一半：1000 台的站内 jitter 只有 ±0.01°，投影到 k=1 后 952 个点里只有 **67 个不同的整数坐标**
   ——缩略图看起来是"52 个城市各一团"，不是"上千台设备"。这两条合起来说明**按站点聚合不是可选项**，
   它是缩略档唯一有意义的画法。
4. **1000 台在明细档已经是 5 fps**（202 ms/帧），滚轮与拖动都会明显脱手；300 台在明细档 56 ms
   也只有 18 fps。按 D3 给的"预期规模上千台 CPE"，现在这版 SVG 画法兑现不了那个承诺。

### 一个标尺（用来把上面的毫秒数落成一个判断：要不要挪 canvas）

同一浏览器、同一台机器，把 N 个 `<g><circle/><text/></g>` 写进离屏 svg 的 `innerHTML`：
100 组 0.6 ms、1,500 组 12.4 ms、3,000 组 28.1 ms、6,000 组 74.9 ms、11,000 组 151.5 ms
（≈14 µs/组，轻微超线性）。强制布局另加 279 ms@11,000 组——这部分**不在**上面量到的帧延迟里，
但它正是他肉眼会看到的卡顿。对照这条标尺，明细档 202 ms 里能归给"重建一万个元素"的量级就是
150 ms 上下（**这是对照推算，不是分段实测**），也就是说 canvas 与裁剪砍的是同一块成本。

### 我建议的下一步（**要你拍，代码一行没动**）

按性价比排，前两条我认为必须做，第三条决定缩略档长什么样，第四条以后再看：

1. **视口裁剪**：每帧只画可见世界框内的节点与连线。按结论 1 的实测比例，14× 时绘制集缩到 ~3%，
   按上面那条标尺推算明细档应从 202 ms 掉到几十毫秒级（**这是推算，不是量出来的**，改完要复跑同一套
   量测）。这是唯一能让"上千台"这个承诺成立的改动。
2. **重绘拆层 + rAF 合帧**：底图（含 665 KB 海岸线）与设备/连线分成两个 `<g>`，缩放平移只重写后者；
   `wheel` / `pointermove` 改成置脏 + 每帧一次 `undMapDraw`。现在每个事件同步重建一次整幅，
   触控板一次惯性滚动能发几十个事件。
3. **缩略与站点两档按站点聚合**：一个站一簇，圆心用站点经纬度（`sites[].lon/lat` 已经在文档里），
   半径或角标 = `sites[].devices`，标签放不下时显示"城市 · N 台"而不是随机某台设备名。
   逐设备只在明细档画。这条同时治结论 3 的两个病。
4. **canvas 只作为 1–3 之后的备选**：如果裁剪 + 聚合之后明细档的可见元素仍然 >2–3k 才考虑。
   以现在的数据我看不到非换不可的理由，所以先不提，等第 1 条复跑量测再判。
5. 另外两条与渲染无关、但同样是"上千台"要还的债，要不要现在处理听你的：
   `/api/underlay/topology` 一次 **1.4 MB** JSON 而且 10 秒一轮询（服务端每次都要拼这份文档）；
   拓扑页与设备页那份**不分页的站点表**（1000 台时 597 行、651 个 `<tr>`，整页 HTML 2 MB）。

### 拍板结果（2026-10-29）

**第 1 条视口裁剪与第 3 条按站点聚合一起做**：结论 1 和结论 3 是同一个病的两面——每帧重建整幅、
缩略档又没有地方放逐设备的点，分开做会得到一个"裁剪后仍然要画 952 个站点簇"的中间态。
第 2 条（拆层 + rAF 合帧）与第 4 条（canvas）还没拍，等这两条复跑量测之后再判。
发生器已经挪进 `controller/tools/topo-scale-mock/`，和 `world-basemap` 并列成第三个工具，
这套量测从此可以复跑。第 5 条那两笔债（1.4 MB × 10s 轮询、不分页的站点表）仍然没排。
