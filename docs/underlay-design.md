# underlay 配置模块设计

2026-10-28 与用户逐条对齐后定稿。本文描述设计；模型与分配器的实现在 `controller/internal/underlay`。
配置分三层：基础配置（客户侧，已实现）、underlay（隧道：模型/API/控制台/设备侧 `sr-agent -tunnels` 都已实现，2026-10-28 lab 端到端验证通过见 §11，含零隧道中转盒的 A/B 见 §12）、overlay（路由：草案在 `overlay-design-draft.md`，思科调研在 `cisco-vpn-leaking-research.md`，未开工）。

underlay 三个页面：**全局配置**、**隧道配置**、**拓扑图**。

## 0. 已拍板的决策

| # | 决策 |

| 1 | 隧道标识只存在于控制器内部，用户配置里不出现 |
| 2 | 自动配置 = 批量把手动那套配一遍；已存在的设备对直接跳过 |
| 3 | 只有 overlay 地址池；控制器不分配 WAN 地址（WAN 地址由设备配置并上报） |
| 4 | UDP 端口有默认池（避开内核临时端口段），也可手填覆盖；端口只在同一台设备内唯一 |

| 9 | 密钥、槽位、BFD 多跳等由控制器内部决定并下发，不做用户配置项 |

| 11 | MTU / MSS 不属于本模块：MTU 在基础配置的接口上，MSS 按隧道 MTU 自动钳制（已实现） |
| 12 | 变更必须 diff + 二次确认；overlay 随隧道自动变化；auto 和 manual 没有覆盖关系；没有 full-mesh ↔ hub-spoke 的切换；删除只在手动表单与拓扑图里做 |
| 13 | 全局配置是**租户级**的，运营方不可见 |

| 19 | 手动创建隧道：本端单选、**对端可多选**（同一端、同一份路径逐对端各建一条，建成/跳过分别回报），场景就是「从 CPE A 经同一条路径到 B C D E F」 |

## 1. 全局配置（租户级）

| 字段 | 默认 | 说明 |
|---|---|---|
| `vpn_port_min` / `vpn_port_max` | 20000 / 29999 | 隧道监听端口池。必须避开内核临时端口段 32768–60999 和 1024 以下 |
| `vpn_port_exclude` | 空 | 排除段列表（个别设备上被别的服务占用时，或运维习惯） |
| `transit_port_min` / `transit_port_max` | 15000 / 15999 | 中转端口池，与 VPN 端口池不重叠。租户内所有设备优先用范围内第一个值 |
| `overlay_cidr` | 10.250.0.0/16 | overlay /32 池，一条隧道两端各取一个 |
| `probe_interval_ms` | 300 | 隧道内探针发送间隔 |
| `bfd_min_tx_ms` / `bfd_min_rx_ms` | 50 / 50 | BFD 最小发送/接收间隔（字段单位是毫秒，下发时换算成微秒） |
| `bfd_detect_mult` | 3 | 连续丢失多少个包判定 down |

规则：

- **没有发布全局配置就不能建隧道**，隧道页给出直达全局配置的入口。默认值内置，"恢复默认"只填回输入框、仍需保存。
- 发布是"设备开始监听中转端口"的时刻：每台已入网设备在这里拿到自己唯一的中转端口并随配置下发；此后重新发布不搬动已分配的值。客户不会一次把设备全装完，所以发布之后入网的设备在**入网那一刻**补分配（`State.EnsureDevice`），心跳再兜一次底：入网时池子不够、或设备记录早于这个规则，下一次心跳就修好。补分配会推进 underlay generation，设备因此重新拉 bundle；未发布时入网什么都不分配。
- 修改只影响**新分配**：已分配的端口和 /32 不重排、不断流。新池放不下现有分配时，保存前拒绝并指出是哪条隧道，而不是在后台把它改掉。
- 页面显示派生只读信息：端口已用/总量、overlay 已用/总量、最近一次分配失败原因。
- `overlay_cidr` 必须与基础配置里任一 VPN 的接口子网、静态路由前缀不重叠（overlay /32 落在 table 250，与客户 LAN 撞段会让下一跳解析走错表）。

## 2. 隧道数据模型（控制器内部）

```text
Tunnel
  id            控制器生成，不暴露给用户输入
  a / b         设备端：
                  device_id     已入网设备
                  iface         物理端口名（基础配置里的接口名，例如 eth0）
                  addr          选填，外层地址；空 = 用 reflector 观测到的地址
  port_a/port_b 两台设备各自监听的 UDP 端口，来自池子，可手填覆盖
  overlay_a/b   两端 overlay /32，来自池子
  path          空 = 直连（0 跳）；否则 1..3 跳的**有序**中转链，两种写法二选一：
                  template_id                    引用路径模板（多条隧道共享）
                  hops[]{device_id, addr}         内联，只影响这一条；addr 空 = 观测值
                  顺序就是行走顺序（hops[0] 是第一跳），控制器不重排；
                  中转端口不进 path：它属于设备，下发时按设备查，重新绑定后不会留下旧端口
  tunnel_mtu    只读，由两端上报的 underlay MTU 与**最坏段数**算出（wire.TunnelMTUBudget）
  roles         { a: hub|spoke, b: ... } —— 那批 auto 在这条边上的角色，仅供显示
  batch_id      可选，仅用于回溯这批自动编排；不参与判重、不参与覆盖
  created_at / updated_at
```

旧数据里 path / PathTemplate 的单跳写法（`device_id` + `addr` 平铺）在读入时折叠成只有一跳的 `hops`；同一份 JSON 里两种形状同时出现直接报错，不猜以哪个为准。写回只有 `hops` 一种形状。

PathTemplate（租户内可复用的一条**有序**中转链）：`id`、`name`、`hops[]`（1..3 跳）、`created_at`。
被隧道引用时不允许删除（否则等于悄悄把这些隧道改回直连）；编辑模板立即作用于所有引用者，保存前显示引用条数。

- **一个设备对只能有一条隧道**：创建时按设备对（不分方向）判断，已有就直接 409 拒绝并说明原因。根因是密钥粒度——每台设备只有一把静态 WG 密钥，VPP 的 peer 表按公钥跨接口去重（-116），同一对设备的第二条隧道装上去会被数据面拒掉。自动编排算出的设备对若已有隧道，静默跳过。
- `roles` 不是节点属性：同一台设备在第 1 批里可以是 hub、第 2 批里是 spoke，两条边各记各的。不存在"节点角色"这个持久对象。
- 隧道状态（up/down/未知）不落配置，来自遥测（每隧道 BFD + 探针）。设备心跳另带一份 `wire.TunnelState`（本机装了几条、装的是哪一代、跳过几条、失败原因），那是设备自述，不是控制器从"已发布"推断出来的；逐条 up/down 还没接上——遥测行按数据面接口索引记账，控制器还没把每一行对到某条隧道上。
- 一条隧道的 path 最多 3 跳（3 个中转设备），按 `hops[]` 的顺序行走。3 是策略上限，取拍板时"能实测到的深度"那一档，不是数据面极限：段表 8 段、一段留给隧道终点，物理上能到 7 跳。超上限直接拒绝并说明段预算，不静默截断。已 lab 实测过的是 1 跳中转（§12）；多跳的实测结果另见验证章节。
- `tunnel_mtu`：**只看两端上报的 underlay MTU，不看这条隧道路径当前几跳**，取已知一侧的较小值后按 `TunnelMTUBudget(underlay_mtu, wire.MaxSRSegments)` 算，再与 `wire.MaxTunnelMTU` 夹取；算出来低于 `wire.MinTunnelMTU` 直接拒绝创建并说明余量。理由是设备侧 `NewLink` 无条件按最坏段数校验（接口只有一个 MTU，而段列表随时可被改写；超出预算不会报错，是内层每片各自再套一层 WG+SR 头、外层又分片，静默丢包）。早先按"当前跳数"算的设计在 lab 里让每一条控制器管理的隧道都装不上：1500 的链路发 1440，设备只接受 1368。改 path 只重算 `updated_at`，不动 `tunnel_mtu`。没有需要用户填的 MTU 字段。
- 只有一侧上报接口 MTU 时按那一侧算；**两侧都没上报**时 `tunnel_mtu` 记 0（未知），下发回退到 `wire.DefaultTunnelMTU`（1360）并在界面标明"默认值"，不假装是算出来的。

## 3. 自动编排

输入：选中的已入网设备集合 D、模型、hub（hub-spoke 时）、"spoke 间隧道"档位。

| 模型 / 档位 | 建立哪些隧道 | 条数（h + s 台，n = s+1） |
|---|---|---|
| full-mesh | 所有设备两两直连 | n(n-1)/2 |
| hub-spoke / 无 | 只有 hub↔spoke，直连 | s |
| hub-spoke / hub 中转 | 全 mesh；spoke↔spoke 的 path 指向 hub；hub↔spoke 直连 | n(n-1)/2 |
| hub-spoke / hub 仅中转 | 只有 spoke↔spoke，path 指向 hub；hub 不建任何隧道 | s(s-1)/2 |

"仅中转"就是 lab 里 `lab-transit` 的形态：它没有 WG 隧道、不参与加解密，只作为 SR 路径里的一跳。

编排前剔除并如实报告：

- 设备离线或观测过期（超过保鲜期没有新的外层地址）；
- 两端都是对称 NAT 的设备对：这类隧道不可能建立（中转也不改外层源，救不了）；
- 缺少观测到的外层地址（刚入网，reflector 还没看到它的出口）；
- 设备没有上报可用的物理端口：auto 不问用户，用设备上报的默认出口；没有就跳过这一对；
- 该对已有隧道（一个设备对只允许一条）；
- 端口池或 overlay 池分配失败：跳过这一对并报原因，已分配成功的不回滚；
- 选中设备不足 2 台、hub 不在选中集里、"hub 仅中转"少于 2 台 spoke。

一端是对称 NAT 时仍然建，但该隧道标"由对端先发起"：只有 NAT 侧能主动打洞，对端靠 WG 的动态 endpoint 更新回包，两端的 keepalive（默认 25s）必须保持。

确认前必须展示：将新增多少条、跳过多少条（及原因）、overlay / 端口消耗、每台设备的隧道数。预览用与落库完全相同的分配路径计算，所以预览里的端口和 /32 就是确认后拿到的值。

hub-spoke 的 spoke 间隧道共用一个自动生成的路径模板（`经 <设备名> 中转`），同一 hub 的后续批次复用它——这样改一次模板，两批的 spoke 间隧道一起移动。

## 4. 手动配置表单

字段：本端设备、本端物理端口、本端地址(选填)、**对端设备（可多选）**、对端物理端口、对端地址(选填)、UDP 端口（显示自动分配值，可改）、路径（选填）：直连 / 内联有序中转链（1..3 跳，可增删改序）/ 选一个路径模板。中转地址默认用观测值，可填指定地址；内联链可以"存为模板"，供后续隧道复用。

- 多选对端 = 批量：本端与路径写一次，每个对端各建一条**完全等同手动单条**的隧道（同一套校验、同一个分配器、同一句拒绝）。响应是 200 而不是 201，带 `batch_id`、`tunnels[]`（建成的）与 `skipped[]`（没建成的对端 + 原因），两者相加等于去重后的对端数——页面要能报出一笔对得上的账。
- 只对**所有对端都成立**的错误（本端没入网、路径模板不存在、跳数超限）才整批拒绝，一次报清；某个对端自己的问题（已有隧道、同时是中转、自连）是一条跳过，不回滚已经建成的那些。
- "存为模板"和批量同时出现时：整批一条隧道都没建成就删掉刚建的模板，不留没人引用的名字。
- 单选对端时保持原语义（只写 `b.device_id`，不填 `peers`），页面不需要为了批量牺牲单条的姿势。

- 地址选填的含义：空 = 用 reflector 观测到的外层地址；填了 = 明确指定，展示上标"手填，非观测值"。
- 同一对设备不能建第二条（见 §2）；换了端口也不行，原因在密钥粒度，不在端口。
- 表单与拓扑图的编辑共用同一套字段、同一条校验路径。
- 模板下拉显示模板名、中转链（按顺序的设备名）、当前引用条数；删除模板前必须先把引用它的隧道改掉（否则等同于把它们悄悄改回直连）。
- 编辑模板的中转链是**有序**控件：能加到 3 跳、能上下移动、能删；把它改成另一台设备或另一条链，引用它的所有隧道一起移动（保存前显示会动到几条）。模板改动不会替新加入的中转设备补分配中转端口——端口归入网/发布那两件事管，补发会把运营方清零的值又发回去；这一跳没有端口时由下发环节报出来。
- 保存立即生效（隧道不是草稿公文，见 §8）：controller 的 underlay generation 自增，设备下一次心跳看到 `tunnel_version` 变了就自己来拉。设备侧由 `sr-agent -tunnels` 落地，不需要"发布"这一步。

## 5. 拓扑图

- 节点 = 已入网设备；边 = 隧道。
- **"仅中转"设备没有隧道边**，所以图必须有第二层信息：隧道的 path。画成虚线跳接（spoke→hub→spoke），否则该节点在图上不可见、也看不出它承载多少流量。
- 状态只来自遥测：up / down / 未知（没上报）。没上报就是"未知"，不画成断、不画成 0。
- 一个设备对就是一条边，也就是一条隧道。拓扑接口仍按 bundle（每对设备一组，`count` 恒为 1）返回，是为了将来放开多隧道时前端不用改形状，不代表现在允许。
- 交互：点边 → 编辑（手动表单）/ 删除（二次确认）；点节点 → 设备概览（端口占用、隧道数、观测地址与时间、是否被当作中转）。图上没有"新建 auto"入口，批量编排留在隧道页。
- 底图是**自带**的：Natural Earth 几何在生成时就预投影成固定 viewBox 的 SVG 路径，运行时零库、零瓦片服务、零 node 依赖（110m 常显 131,914B，只有放大过 4.5× 才按需拉一次 50m 的 681,448B）。运行时那 12 行投影公式与 d3-geo `geoNaturalEarth1` 在九个城市上逐点一致（误差 0.000000px）。选型对比、拆分与"怎么算验证过"见 `docs/topology-map-plan.md`。
- 信息密度随缩放分三级（缩略 / 站点 / 隧道明细），线宽与字号按 `1/k` 反算，所以任何倍率下墨迹粗细恒定；缩略层的站名"放得下才画"，不是等某个倍率才出现。
- **逻辑视图保留**（双视图开关）：lab 里设备都在同一台 Docker 主机上，地理视图会挤成一个点，能用的那张反而是逻辑的环形图。
- 节点的位置来自站点（§14）。没有站点的设备**不进图**，进右下角"未定位设备"清单，位置一栏写"未上报"——控制器不猜坐标。

## 6. 分配器

**UDP 端口（VPN 池、中转池各自独立）**

- 取池内**最小空闲**端口；释放立即回池，不做冷却。端口号不携带**跨设备**身份（隧道身份是 WG 密钥与对端公钥，旧会话的残留包过不了新 peer 的校验），但它在**本机**就是数据面的绑定键：`set sr-wg tunnel <idx> path <p> src-port <本端监听端口>`，encap 按外层 UDP 源端口查这张表，同一台盒子上两条隧道不能填同一个本端端口。
- 中转端口：发布全局配置时给每台已入网设备取池内第一个值（租户内尽量一致），被本机别的监听占用就顺延；发布之后入网的设备在入网时按同一条规则取号。设备侧绑定失败时把 `(设备, 端口)` 记为不可用再顺延，不回收这个判断。
- 一台设备的中转端口一旦分配就固定；同一台设备再出新的中转隧道，复用同一个端口（数据面按 SR 头转发，与端口无关）。
- VPN 端口在创建隧道时分配；没有已发布的全局配置就没有中转端口，因此也建不了隧道。

**overlay /32**

- 语义是持久化 FIFO：分配取队首，释放按固定顺序追加到队尾。实现上不存 65k 个字符串，而是存"下一个从未用过的地址"游标 + 释放队列；效果与字面 FIFO 相同，状态体积只与已分配量成正比。
- 理由：overlay /32 会进对端的路由与下一跳，立即复用会让旧路由悄悄落到新隧道上；队尾插入保证"用遍一圈才轮到它"，且不需要任何超时参数。
- 一条隧道一次取两个（a、b），删除时按 a→b 回队尾；游标与队列落盘，重启不重排。
- 跳过网络/广播地址；空闲低于 10% 告警；耗尽时创建失败并说明原因，自动编排则跳过这一对（已成功的不回滚）。

## 7. 校验清单

自环（A == B）；同一设备对已有隧道（409，见 §2）；全局配置未发布；设备未入网 / 离线 / 观测过期；设备没有上报物理端口（手动必须选一个，auto 直接跳过）；物理端口不在该设备上报的接口列表里；UDP 端口不在池内、已占用、等于该设备的中转端口、落在排除段；中转设备未入网 / 离线 / 就是 A 或 B；路径模板不存在，或仍被隧道引用时删除；overlay 池耗尽或与 VPN 前缀重叠；两端 underlay MTU 算出的 `TunnelMTUBudget` 低于 `wire.MinTunnelMTU`；单设备隧道数超过上限；自动编排选中设备不足 2 台或缺 hub；批量条数超过租户上限（确认前算好）。

## 8. 下发与设备侧（已实现）

**通道**：`GET /v1/underlay/bundle`（设备证书鉴权，只能拉到自己那台的）。心跳里的 `tunnel_version` 就是租户 underlay generation（`underlay.State.Gen`），隧道/模板/全局配置任一改动都自增；设备发现与本地跑的不一致就来拉。控制器从不主动连设备——盒子在 NAT 后面。

**与基础配置通道的区别**：基础配置有草稿→发布，隧道没有。隧道是"建了就存在"的活对象，端口和 /32 在创建时就分配好了，所以每次改动就是新的一代。唯一的闸门是全局配置未发布时根本建不了隧道（没有中转端口，见 §1）。

**包内容**（`wire.UnderlayBundle`，一台上的一份完整快照，不是增量）：

- `version` / `overlay_table`(250) / `transit_port`（这台设备的中转端口，0 = 它不做中转）；
- `p_keys`：租户的逐跳 MAC 密钥环；
- `tunnels[]`：每条隧道只含**本端该建的那一半**——`instance`（WG user_instance，1000+t 序号）、`path_id_base`、出口 `iface`（按名字，VPP 重启会重排索引）、本端 `listen_port`、`peer_endpoint`（ip:port）、两端 `overlay`、对端证书与公钥担保、`relays[]`（**有序**中转链，每元素 = `{node_id, endpoint}`，endpoint 是那台设备的 `观测/手填地址:它的中转端口`；直连时字段整个不出现，不是空数组——agent 用 `len(relays)==0` 判断"无 SR 跳"）、`mtu`、`underlay_mtu`、`src_ip`（只在控制器能证明该口拥有这个地址时才给）。
- `skipped[]`：配置了但这一代描述不完整的隧道 + 原因（对端没证书 / 没上报公钥担保 / 没有外层地址 / 中转没端口 …）。**不是错误**：一台设备的对端不可用不能拖住这台设备上其它隧道。

**设备侧**：`sr-agent -tunnels`（必须同时给 `-vpp-api`，applier 走 VPP 的 api socket）。`agent.TunnelSync` 把快照变成数据面状态，三条规则：

1. **全量对齐**，不记本地状态文件——VPP 本身就是记录。丢一次拉取、agent 崩过、VPP 重启过，下一份快照都能收敛。
2. `skipped` 里的隧道**保持现状继续跑**：观测地址短暂过期不是拆掉一条正在过流量的链路的理由。
3. `user_instance >= wire.UnderlayInstanceBase` 且快照里不再出现（`tunnels` 和 `skipped` 都没有）的接口，才删除——在 agent 停机期间做的删除也能落到设备上。这条孤儿清理只碰自己管的实例号段，人手工配的接口不动。

落地顺序按 VPP 的约束：ip table add → (地址已存在先 del) → set interface ip table → add overlay /32 → admin up → mpls enable → 最后加 peer；随后 `ip route add table 250 <peer_overlay>/32 via <if>`；有多跳中转时 `AddPath`（表里**只写 `relays[]`**，agent 侧 `relays[0]` 是第一跳，进 vppapi 时**倒序**，所以数组最后一格才是第一跳——顺序反了包会先弹到错的盒子上；隧道终点不在表里，encap 从报文外层 dst 现取）+ `BindTunnel`（键 = 本端监听端口，`src_port`）+ `EnableEncap`。MSS 按隧道 MTU 自动钳制，MTU 只核对不覆盖。

**VPP 重启**：vppapi 客户端没有自动重连，socket 死了就是 `ErrClosed`。`TunnelSync` 会把坏连接丢掉，并在下一次 reconcile 时用 `vppapi.Dial` 重新连（快照里对不上就重建）。观测回报与 applier 共用这一条连接：重连后回报也跟着新连接走，不会抱着一个已经消失的 socket。心跳里的 `tunnel` 为 `null` 表示这台设备根本没有数据面（`-tunnels` 和 `-vpp-api` 都没开），`capable:false` 表示"有这个通道但被关掉了"（只开了 `-vpp-api`）——控制台按这两种情况分别写文案，不把"没有这功能"和"没装上"混成一句。

**回执**：心跳里的 `wire.TunnelState`（`capable` / `version` / `applying` / `ok` / `error` / `tunnels` / `skipped` / `applied_at`）是设备自述装了几条、装的是哪一代。控制台的设备表有一列「隧道下发」直接显示它，失败原因原样带出；隧道级的 up/down 仍来自遥测，尚未接到具体某条隧道上（见 §2）。

**手工路径**：老的"下载配置包 + `sr-apply`"只管基础配置，**不含隧道段**。要让设备装隧道，必须跑带 `-tunnels` 的 agent；没有 controller 的场景目前仍按 lab 脚本手配 VPP。

## 9. 明确不做

- 优先级/度量、策略选路（overlay/策略模块的事）。
- PSK、加密套件、密钥轮换的用户配置。
- MTU / MSS 的用户配置。
- 运营方视角的池子管理（租户完全隔离）。
- full-mesh ↔ hub-spoke 互换、池子变更触发重排。
- 超过 3 跳的中转链：数据面按段数能到 7 跳，但 4 跳以上没有实测依据（延迟、逐跳弹段计数、内层分片行为都没测），所以策略上限卡在 3。
- 自动隧道被删后不重建的保护（没有墓碑；重跑会重建，发布提示里说明）。

## 10. 默认选择（已按此实现）

- 一条隧道的中转上限是 **3 跳**（`underlay.MaxRelayHops`）：拍板时选的是"能实测到的深度"这一档，不是数据面硬顶 7 跳。`MaxRelayHops + 1 ≤ wire.MaxSRSegments` 由单测锁住——真要加深，先测再改这个常量。MTU 与跳数无关（按最坏段数算），加深不需要重发 MTU。
- **一个设备对一条隧道**：本增量每台设备只有一把 attest 过的静态 WG 密钥，VPP 的 peer 表按公钥跨接口去重（-116）。要放开"同对多隧道"，得先把密钥粒度改成每隧道一把（`internal/underlay` 里那条拒绝和 §2 的模型注释都要一起改），不是加个字段就行。
- 中转设备离线时，自动编排**跳过**相关隧道并报"中转设备离线"，不建一条注定 down 的隧道（早先设想的"照建并标风险"没有采用：没有风险标记字段，跳过对用户更可操作）。

## 13. 自动编排在这套 lab 里的实测边界（2026-10-29，只跑了预览）

`POST /api/underlay/auto/plan`（不落库，与 apply 同一条分配路径）对 `nodes:[2,3,4]` 的三种模型：

| 模型 / 档位 | pairs | add | skip 原因 |
|---|---|---|---|
| full-mesh | 3 | 0 | 2↔3「这对设备之间已经有隧道」；2↔4、3↔4「缺少观测到的外层地址」 |
| hub-spoke / via-hub（hub=4） | 3 | 0 | 同上 |
| hub-spoke / hub-transit-only（hub=4） | 1 | 0 | 只有 spoke↔spoke 这一对（s(s-1)/2 算对了），原因是「已经有隧道」 |

结论分两层，别混起来看：

- **逻辑侧没问题**：配对数量、hub 档位、"一对一条不重复"、每设备隧道数（`per_node`）与消耗（`usage`）都按 §3 报出来了。
- **这套环境一条也建不出来，而且是设计使然**：lab 里没有 reflector，`observed_addr` 全空，而自动编排的寻址来源**只有 reflector 观测**（`plan.go` 的 `va.Observed == ""` 那道门）。手动表单里"地址选填"那条口子在 batch 里没有对应物 —— 手填地址进不了自动编排。所以 §11/§12 建出来的隧道是手敲地址的产物，auto 只能报跳过。
- 待用户拍板的那条（数据面自报的 `sr_obs` 要不要当寻址来源）就是这一格的钥匙：cpe1/cpe2 互相已经观测到对方的外层源并且 `attributed` 成功过，只是控制器不把它当地址用。

顺带两处代码层面的事实（读出来的，不是 lab 跑出来的）：

1. 中继跳的地址在 auto 里固定留空（`hubTemplate` 建的是 `Addr:""` 的模板），意思就是"下发时用中转设备的观测值"。可**观测门的顺序在解析 relay 之前**：两端有观测、hub 没有时，这一对不会被跳过，而是建出一条隧道再由设备侧按条报 skip 原因。不是静默错，但把"这条隧道注定装不上"推迟到了下发那一跳。
2. 预览的 `add/skip` 里没有"这台设备还没有 WG 公钥担保"这一类原因的显式档位（下发时才有），所以预览条数可能与实装条数不一致。

## 14. 站点（设备位置），2026-10-29 已落地

给地图补的那一层数据，边界比接口本身重要：

- **模型**：`site{id, tenant_id, name, lon, lat, created_at_unix, updated_at_unix}`，设备行只存 `site_id`。选站点表而不是每台各填经纬度，是因为预期规模上千台 CPE：一个机房录一次、搬迁改一次全站生效，而且"同址设备各写各的坐标"这种没有机制阻拦的事就不会出现。
- **只用于画图与运维认路**（D2）：位置**不进** `/v1/underlay/bundle`、不下发设备，设备侧契约一字未动。这条不是靠前端不显示，是 `TestSiteNeverReachesADevice` 按字段名盯住的。
- **运营方看不到位置**同样是结构性的：站点挂在 `/api/state` 的 `runtime` 里，而运营方那份节点副本从不填 `runtime`；`TestStateCarriesSiteForTenantOnly` 盯住"租户有、运营方整块没有"。
- **接口**：`GET/POST/PUT /api/underlay/sites`、`POST /api/underlay/sites/delete`、`PUT /api/underlay/node-site`（放设备进去或清掉）。每次写入都回**全量站点清单 + `unplaced_nodes`**，前端据此刷新列表并让拓扑缓存失效——刚挪了位置的设备不能还画在老点上。删除只对 0 台设备的站点开放，否则 409 带上还有几台。
- **经纬度是手填的**：控制器不测量、也不猜。空值被拒（`(0,0)` 是几内亚湾的真实坐标，填 0 会被画到那里），非数字与非有限值也被拒；lab 里给不同城市手工填坐标是被允许的（D6），值只进 lab 运行时数据。

## 15. 两跳中转（3 段）的 lab 端到端（2026-11-02，已通过）

§12 只证明了单跳中转（2 段）。多跳的路径是**有序**的，顺序错了照样能"通"（只是绕路或走错盒子），所以这一轮用 trace 盯住每一跳的 `seg_left` 和 `next_hop`，而不是只看 ping。

环境：租户 `tenant-a` 的 node 1–4，四台都跑 `sr-agent -tunnels`。中转端口 `15000`（§0 决策 5），WAN 接口 cpe1/cpe2/transit = `host-eth1`、cpe3 = `host-eth0`。建隧道 t6（控制台手动，有序两跳；两端地址手填，`matches_observation:false`）：

| 项 | 值 |
|---|---|
| 端点 | node 1 `lab-cpe1` 10.88.1.11（overlay 10.250.0.7） ↔ node 2 `lab-cpe2` 10.88.1.12（overlay 10.250.0.8） |
| 有序中转跳 | `[node 3 lab-cpe3 10.88.1.13, node 4 lab-transit 10.88.1.3]`（**cpe3 先被命中，transit 后**） |
| MTU | 1368（`mtu_is_default:false`，按最坏段数预算，与跳数无关） |

两端 `show sr-wg paths` 各一条 3 段路径，`seg[0]` 是终点、`seg[1..2]` 是跳，顺序就是表单里的顺序：

```

      seg[0]: 10.88.1.12:20000   seg[1]: 10.88.1.3:15000   seg[2]: 10.88.1.13:15000
cpe2  path_id=1001 seg_count=3
```

cpe3 收到的包 `seg_left=1/3`、把下一跳指到 transit；transit 收到的包 `seg_left=0/3`、下一跳就是隧道终点的 VPN 端口（20000）。两端 `err=0`，`show sr-wg stats` 的 `hmac_fail/seg_exhausted/bad_*` 全 0，收端 `Decap ok` 持续增长。**不要用 `Transit: ok` 的差值当证据**：隧道里 50 ms 的 BFD 一直在打，计数器会被背景流量淹没；干净的判据是 paths + trace + 端到端 ping。
