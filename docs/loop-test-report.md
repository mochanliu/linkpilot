## 0. 一页结论

**0.1 环境按要求搭起来了，配置动作基本是从控制台做的。**
4 台 CPE + 3 台客户路由器 + RR + 控制器；full-mesh(1,3,4)、hub-spoke(2 为 hub 连 3、4，spoke 之间不连)；1/2 同站点（HA 形态）；3、4 各播一个 loopback；1/2 与 cust12 跑 OSPF area 0。配置一遍共 **46 次业务写请求**（另有 18 次 login/logout 会话往返，合计 64 次写，全部 2xx），逐条见 §2.1。
三处不是控制台路径（逐条原文在 §2.5）：一是隧道自动规划把 5 条配对**全部跳过**（原因原文见 §2.2），只能用手工建隧道接口补齐；二是 sr-fib 的隧道表（下一跳↔接口名）在产品里根本没有下发段，只能在盒子本地 `PUT /config` 填（§2.5a、G-2）；三是 4 台盒子的 sr-route/sr-fib/sr-frr 是脚本手起的，而且起之前必须先手工跑一次 `sr-apply boot` 重放才能把 `/etc/sr-frr.json` 落盘——**首次发布是个死结**（§2.5c、G-5，判拍 P-13）。

**0.2 没有一个"干净基线"可测。**
22:08 那份"正常态"抓表里，4 台盒子有 3 台缺客户前缀：cpe1 缺 `172.16.4.1/32`、cpe3 缺 `172.16.12.1/32`、cpe4 缺 `172.16.12.1/32` 与 `172.16.3.1/32`。缺的原因盒子自己写在日志里——**BFD 会话那一刻不是 Up，sr-fib 就把这条路径跳过了**（§3.4、§3.5）。

**0.3 根因量到了，而且分成两半。**
- **触发源在宿主**：这台 macOS/colima VM 每 30–45 秒把**所有容器一起**冻住约 3.4 秒。对照实验（§4.2）里，`lp-rr`（没有 VPP）与 `lp-cpe1`（VPP 99% 忙轮询）两个互不相干的 1 Hz 时钟循环，在**同一绝对时刻、同一序号位置、同一幅度**出现停顿；VPP 接口 `rx packets` 计数器在这段时间真的不涨（§4.3）。不是我的观测脚本造成的：完全不采样 CLI、只打六条流的那次（quiet-60，22:37）照样 23–25% 丢包，且六条流在同一段序号上一起丢。
- **放大在我们产品里**，这部分是真缺陷：150 ms 的 BFD 检测时间 + **零 hold-down**（一次抖动立刻撤前缀）+ sr-fib 1 秒轮询 + **BFD 假 Down 之后发包节奏退到 1 秒**（实测 `Transmit interval 1000000`），把这 3.4 秒放大成客户可见的 **1.0–12.0 秒黑洞**，150 秒里出现 8–14 次（§4.4）。换掉这台宿主机也不会消失：任何 ~150 ms 的真实链路抖动走的是同一条放大链。

**0.4 HA 的核心问题找到了：VRRP 没有跟踪任何接口。**
场景 A（关掉 cpe1 的 WAN 口）实测：cpe1 表 0 里的客户前缀被撤干净（172.16.3.1、172.16.4.1 消失、颜色表清空），**但 cpe1 仍是 MASTER、cpe2 仍是 BACKUP，没有切换**。cust12 的默认路由指向 VIP 10.76.12.10，流量继续灌进这台 WAN 已死的盒子——**41.8 秒不间断黑洞**，四条流丢 76–78%，而与站点无关的 3↔4 那条是 0%。两台盒子的 VRRP dump 都写着 `跟踪掉0`（被跟踪接口掉线数 0，因为一个都没跟踪）。
**VPP 26.06 是有这个能力的**：API 消息 `vrrp_vr_track_if_add_del` 存在（每条被跟踪接口可设掉线时降多少优先级），`vrrp_vr_details.runtime.tracking` 也会回报。我们的代码只**读**了跟踪状态（`vppapi/vrrp.go:106 TrackIfDown`），没有**写**入口，配置模型里也没这个字段（§5、§9 G-3）。

**0.5 场景 B（控制台删一条隧道）的代价不局限于那条隧道。**
删掉 t3（1↔3）实测：与它**无关**的 3↔4 掉了 **95%、38.0 秒**；cpe3、cpe4 表 0 里的 `172.16.12.1/32` 一起消失。重建隧道之后 12↔3 仍然 **100% 不通**（20:04 与 20:09 两次复测都是 0/20），盒子内存里还指着已经不存在的那个隧道口（`10.250.0.1 → wg1003`，而 VPP 里没有 wg1003）——**没有人维护这张下一跳↔接口表**（§6、G-2）。

**0.6 回灌实测抓到了一条，这是给你拍防环规则用的正证。**
cpe1 把自己**不拥有**的 `172.16.3.1/32` 当作本地前缀宣告回了 SD-WAN：RR 侧看到 172.16.3.1 的宣告者是 device 1 和 device 3，而 172.16.3.1 的所有者只有 3。同时 cpe1 的防环计数 `own_route=0`——它没觉得自己是在回灌，因为这个前缀在 cpe1 的本地列表里。**"是不是自己的前缀"这个判据在源头就失效了**（§7）。

**0.7 控制台的遥测数字目前全部不可信。**
探针硬编码在表 0 里查找目的地址，而 overlay 的 /32 只在表 250：所有盒子的所有会话都是 `tx=26204 rx=0 lost=26200 loss=100.0%`（G-4）。监控页此刻显示的丢包/RTT/抖动是垃圾数据。这个 bug 没有任何脚本能抓到，是这次手敲 `show sr-wg probe` 才看见的。

**0.8 需要你拍的（不拍就没有下一步）**：① BFD→FIB 的抖动抑制（hold-down / 撤销延迟，P-2+P-3）；
② BFD Down 后退到 1 s 发包这件事归谁（P-1）；③ VRRP 接口跟踪是否接线、跟踪哪个口、降多少优先级（P-9）；
④ sr-fib 隧道表的归属（谁写盘、谁在重启后重建，P-10）；⑤ 回灌判据改成什么（P-5）；
⑥ G-4 的修法要重编 VPP 插件，按硬规则算不算"必然中断"的操作（P-11）；
⑦ 本轮新收拢的三条：**首次发布的死结**（sr-frr 拒绝空表启动 × 第 5 段热更强制，新盒子第一次配不出，P-13）、
控制台要不要"转发面存活"口径（P-14）、坏盒继续向客户宣告前缀算不算产品约束（P-15）。全部见 §11（P-1..P-16）。

**0.9 还没跑的**：半发布（配了一半）、RR 断连、逃生开关、双 BACKUP/脑裂、以及站点 HA 的**切换窗口**本身
（0.4 说明今天根本不会切，所以这个数还不存在），外加"双活↔主备（改隧道颜色）"。
§8 把它们编成场景 C–G 逐个给了注入动作与判据，并更正我起草时的一处口径错误：
**C/D/E 的判据是表项与版本号，不受"基线不干净"阻挡，现在就能跑**；只有需要亚秒级窗口的 F/G

### 1.5 读这些表时的坑（不写下来一定会读错）

1. **`vppctl` 在非 TTY 下每行结尾带 CR**。任何锚定行尾的 grep 都会失配。本报告所有数字都是 `tr -d '\r'` 之后取的。
2. **`show interface` 把第一个计数器打在接口名那一行**（`wg1001 wg1001 4 up 1368/0/0/0 rx packets 127998`）。按"行首是接口名"解析会漏掉 rx packets。
3. **`show errors interface <name>` 不支持**（VPP 26.06）：它先打印全局计数，再回 `interface: unknown input`。要按接口看错误只能对全局 node 计数做差分。
4. **docker bridge 会 SNAT**：隧道表里每一端的 `matches_observation` 都是 `false`、`state` 都是 `"unknown"`。也就是说"外层地址观测"在这个 lab 里永远是错的，这直接影响 §2.2 的自动规划。
5. **VPP 26.06 没有 `show vrrp` 这个 CLI**。VRRP 状态只能读 `controller/tools/vrrp-probe -dump`。而**环境 #2 的镜像里没装这个二进制**（rc=127），要在容器里 `go run ./tools/vrrp-probe -dump`。本报告里所有 VRRP 行都来自环境 #1。
6. **FIB 全文的头行长这样**：`ipv4-VRF:0, fib_index:0, …`，前缀行**顶格无缩进**。按 `== ipv4-VRF:` 那种摘要行去解析会一个都取不到（我第一版就这么翻车的）。
7. **`sr-fib` 的 `status.last` 不是快照**：`warnings` 和计数器都只反映"最后一轮"，而且两者不一定同一轮（实例见 §6.7，缺陷编号 D-15）。判断"此刻在不在表里"只能看 `show ip fib`。
8. **`sr-route` 的 `dropped_*` 是累计值，`sr-frr` 的 `injected/reported/dropped_loop` 是每轮值**。前者只会变大，后者会被下一轮覆盖——所以同一个计数器在不同抓表里可以上下跳（§7 的实测：cpe1 的 `dropped_loop` 在 19:47 读到 2、19:51 读到 1）。用它们做"发生过几次"的结论之前，先看它是哪种。
9. **`vpp ip fib 摘要` 这一列是白名单产物**（`loop-capture.py:69` 的 `fib_digest` 只留本机自己的 overlay /32 和三个客户 loopback），它**不会**列出远端 overlay 下一跳。摘要里"没有"不等于表里"没有"，一律看 `vpp ip fib 全文`。
10. **FRR 表格最后一列那个 `01:32:27` 是"这条路由学了多久"，不能当时间戳**。同一台盒子、同一份 `show ip route`，这一列在不同抓表之间会漂——§7.3 有实测：172.16.3.1 那条 `O` 路由 19:47:09 显示 `01:32:27`、19:51:43 显示 `00:10:50`，反推"学到时刻"**倒退 53 分钟**。所以本报告里"什么时候发生"一律用**文件 mtime + 控制台请求日志**定时（§10），不用表内这一列（缺陷编号 D-13）。顺带一条同类的坑：设备回报里的 `uptime_sec` 是 **sr-agent 进程自己的**运行时长（`controller/cmd/sr-agent/main.go:283`：`time.Since(processStart)`），不是盒子开机时长，更不能拿它反推事件时刻。

### 1.6 打流的两个口径（混用就会得出错误结论）

`test/lab/loop-probe.py` 两种模式，输出成对落在 `run/loop/probe/<标签>.md` + `.json` + `.raw.txt`：

- **`snap`（安静口径）**：六条流**逐条**打，每条 20 包、间隔 1.0 s。用来量"通不通、丢包水平、RTT"。

六条流 = 三个客户 loopback 两两互 ping：12↔3、12↔4、3↔4（各双向）。

### 2.5 三处不是控制台的介入（必须点名）

除了 §2.2 的手工建隧道（那个还在用控制台的 API），整个过程有**三处完全绕开控制台**的操作。按硬规则它们必须写出来，不能藏在"环境搭好了"这句话后面：

**(a) 盒子本地的 `PUT /config` 填 sr-fib 的隧道表 —— 这就是缺口 G-2。**
`test/lab/loop-bringup.sh` 头部第 P-7 段之后有一句原话（`loop-bringup.sh` 第 1–35 行）：

> "唯一的例外是 sr-fib 的 fib.json……产品里没有它的段，只能在盒子本地 `PUT /config`，由 `loop-fib-sync.sh` 填，报告里作为缺口 G-2 点名。"

**(b) cust12 / cust3 / cust4 三台"客户路由器"的配置是手工塞进 FRR 容器的。** 这三台不是我们的设备、没有 agent、不在控制器里，配置是 `run/loop/cust{12,3,4}.frr.conf` 直接落到容器里 `/etc/frr/frr.conf`。这是合理的（它们模拟客户侧路由器），但要说清楚：**§3.6 里这三台的表项不是控制器下发的，控制器也看不见它们。**

**(c) 首次发布的死结：靠手工"boot 重放 + 手起 sr-frr"绕过 —— 这就是缺口 G-5。**
4 台盒子的 sr-route / sr-fib / sr-frr **既不是 agent 拉起来的、也没走产品的开机清单**：`loop-bringup.sh` 全文没有调用过 `deploy/sr-box/start.sh`，是它在 `stack` 段里先 `pkill -x`（`stop_proc`，`:192-196`）再 `sr-route/sr-fib/sr-frr -config … > /var/log/*.log &` 逐条手工起的（`:525-528`）。起之前必须先做一步手工动作，脚本里把原因写得很清楚（`:519-521`）：

> "先把控制器那份包**重放**一遍（= 盒子上 start.sh 的那一步，只落盘不热更）。非做不可的原因：第 5 段的自动路径要求 sr-frr 活着才肯写 /etc/sr-frr.json，而 sr-frr 又拒绝带着两张空表启动 —— 首次发布的这个死结见环路报告 §9 G-5。"

（这句原文写 bringup 脚本时编号还是"环路报告 F-2"，那个编号在本报告里根本不存在，本轮已按 §9.4 第 3 条改成 G-5。）

这个死结在代码里是两条硬约束叠出来的，不是我推测的：

- 在线 apply 一定要推活进程：`applySrfrr(ctx, inst, prev, !a.NoSrfrrPush)`（`controller/internal/apply/apply.go:532`、`:569`），`NoSrfrrPush` 只有 `sr-apply --no-srfrr-push` 这一个命令行开关会置位（`cmd/sr-apply/main.go:114`），agent 那条路径没有；推的方式是拨 unix socket（`internal/apply/srfrr.go:198-201`），**推失败就直接 return，`/etc/sr-frr.json` 一个字都不写**（`:113-117`：`sr-frr 热更失败（%s 未改动，活进程还是旧表）`，然后 `:124-129` 才是写盘）。设计意图写在同文件头注释里，是刻意的："A PUT that fails fails the apply … saying 已落盘、未热更 would be a lie"（`:11-15`）。
- sr-frr 又拒绝在两张表都空时启动：`cmd/sr-frr/main.go:696-700`，`export_vrfs` 与 `import_rules` 都为空 → `log.Fatal("sr-frr: export_vrfs 与 import_rules 都为空，无事可做；检查配置")`。

所以顺序上是个环：**要写 `/etc/sr-frr.json`，sr-frr 必须先在跑；要 sr-frr 在跑，`/etc/sr-frr.json` 必须先非空；而让它非空的那一步正是"要 sr-frr 在跑"的那一步。** lab 里的解法是把两份文件先落盘：`boot` 路径的 `applySrfrr(..., false)` 明确不推（`apply.go:609-612`，注释 "start.sh launches it after apply, so no push"），于是手工跑 `sr-apply boot --root /var/lib/sdwan/store --vpp-api /run/vpp/api.sock`（`bringup:522-523`）把控制器那份包写进 `/etc/sr-frr.json`，再手起 sr-frr，此后在线推送才走得通。

两点如实补上：

1. **换一台真机首次入网，同一个死结会再出现一次**，形状是这样的：开机清单 `controller/deploy/sr-box/start.sh` 的 `do_bridge` 有门控——没有 `/etc/sr-frr.json` 就 `SKIP: 这台盒子不做 FRR 双向导入`（`:360-363`），于是 sr-frr 根本不在跑；第一次发布的在线 apply 又必然要推它（`apply.go:569`）⇒ 连不上 unix socket ⇒ apply 失败，而失败发生在写盘**之前**（`srfrr.go:113-117` 在 `:124-129` 之前），所以那份配置永远落不到 `/etc/sr-frr.json`，下一次 apply 依旧失败——**死结，不自愈**。
   产品里唯一的**自动**解套路径是重启这台盒子：`Store.Install` 在 apply 之前就把 `current` 软链指到新版本（`apply.go:537`、`:239`、`:256-268`），所以下一次开机 `do_apply` 的 `sr-apply boot` 会**绕过 push** 直接写 `/etc/sr-frr.json`（`:609-612`），接着 `do_bridge` 才起得来。也就是说"这台盒子必须重启一次才能收第一次路由泄露配置"——人工在设备上敲一次 `sr-apply boot` 也能解，而 lab 里我做的正是这一条（`bringup:522-523`），差别只是不用重启整台机器。**还有一条连带后果**：apply 在 sr-frr 这步失败后，排在它后面的 VRRP 那段不会执行（`apply.go:574-576` 的 `if err == nil`，注释写着"半落地的盒子不该拿到 VIP"），所以站点 HA 的 VIP 也在同一个死结里出不来。
   `bringup:445-453` 手写的那份 `export_vrfs: []` / `import_rules: []` 只解决"文件在不在"，不解决"表空不空"——sr-frr 读了照样 `log.Fatal`，所以 lab 里必须等控制台先发布一次、重放之后才起得来。列为 §9 G-5，判拍在 §11 P-13。
2. **当时 agent 侧报错的原文我没留下。** 那次首次发布失败只出现在 `loop-bringup.sh` 的 stdout 里，而这个 session 从一开始就没把盒子里 `/var/log/sr-{route,fib,frr}.log` 与 agent 的 apply 返回值收进 `run/loop/`（§9.3 D-12）。所以上面第 1、2 条是从**代码**证的（行号可复核），不是从当时的日志证的；`boot 重放` 这步实际发生过，是从脚本 `:522-524` 那行 `die` 会中断整个 bringup、而 bringup 跑完了这点反证的。R-1 重跑时会把这几份日志一起收。

## 3. 正常态逐台表项（环境 #2，22:08:29–22:08:53 CST）

抓表脚本 `test/lab/loop-capture.py`，输出目录 `test/lab/run/loop/capture/z-env2-normal/`，每台一个 `<box>.md` + 原始命令输出在 `raw/`。**先说结论：这个"正常态"本身就不正常。** §3.7 有逐条证据。

抓表顺序（每台都一样，这个顺序决定了 §3.7 里"快照错位"的判定方向）：

```
ip -4 addr → ip route → ip route table all → FRR running-config → ospf neighbor
→ FRR ip route → bgp summary → bgp ipv4 unicast → sr-route status → sr-fib status
→ sr-frr status → vpp interface addr → vpp ip fib 全文 → vpp fib 摘要
→ vpp 接口计数器 → vpp bfd sessions → vrrp-probe → agent /status → 盘上三份配置
```

也就是说：**sr-fib 的警告（第 10 项）比 FIB 快照（第 13/14 项）早几百毫秒，FIB 又比 BFD 状态（第 16 项）早几百毫秒**。sr-fib 是 1 Hz 轮询（§1.4），这三项之间差的那几百毫秒足够跨过一次轮询。

九格里 4 格不通。`cust4 → 172.16.3.1` 全丢：对照 §3.4，**cpe4 的 table 0 里根本没有 `172.16.3.1/32`**（被 3 条"路径跳过"里最后那条删了）。`cust12 → 172.16.3.1` 丢 2/3 与 `cust4 → 172.16.12.1` 丢 2/3 是同一个机制：**cust12 有两条等价 OSPF 下一跳、cust4 走 cpe4，选到缺表的那台就丢。**

所以这张表的正确读法是：**它不是在测"链路质量"，是在测"§3.4 那张缺表矩阵的客户可见后果"。** 环境是干净重建的、配置一遍全 2xx、控制台四台全绿、`show bfd sessions` 大部分 Up —— 而客户 ping 不通。

**结论：正常态抓不到"正常"的基线。** 这一条决定了后面的排期：§5/§6 的两个故障场景只能拿环境 #1 已有的结果讲（它们是在一个"整体可用"的环境里注入的），而 §8 里剩下的场景 C–G 必须先把 §4 的病根处理掉才能跑，否则场景效果会被这个背景噪声吃掉、无法归因。

## 4. 秒级黑洞：现象、定位到宿主、以及产品在中间做的放大

这是整个测试里最大的一块，也是 §3.7 "正常态不正常"、§8 "场景 C–G 跑不了" 的共同原因。分两层写：**触发源在 lab 宿主（不是我们的产品）**；**但把一个 150 ms 的抖动放大成 1.0–11.6 s 客户黑洞的机制，全在我们自己的代码里**。两层的证据都是实测的。

### 4.1 现象：六条流的丢包与丢包窗口

### 4.2 对照实验：把"我们代码里的嫌疑"和"宿主"分开

如果只有 §4.1，结论只能到"看起来是共模"。所以我做了两组独立对照。

**(a) 时钟对照：一个完全不碰我们软件的探针**

`run/loop/correlate/tick-rr.txt` 和 `tick-cpe1.txt`：两份一模一样的一行脚本 `while true; do sleep 1; date +%s.%N; done`，分别在 **`lp-rr`（里面只有 sr-rr，没有任何 VPP、没有 FRR、没有我们的 agent）** 和 **`lp-cpe1`（VPP 主线程 99% CPU busy-poll）** 里同时跑 90 个样本，22:37:47–22:39:16。异常点（Δ 偏离 1 s 超过 0.1 s）：

| 样本序号 | lp-rr Δ | lp-rr 时刻 | lp-cpe1 Δ | lp-cpe1 时刻 |
|---|---|---|---|---|
| 18 | −1.422 s | 22:38:03.176 | −1.423 s | 22:38:03.176 |
| 33 | **+3.410 s** | 22:38:20.640 | **+3.410 s** | 22:38:20.639 |
| 77 | −1.454 s | 22:39:02.377 | −1.455 s | 22:39:02.386 |
| 78 | **+3.422 s** | 22:39:05.799 | **+3.421 s** | 22:39:05.807 |
| 87 | −1.419 s | 22:39:12.409 | −1.420 s | 22:39:12.416 |
| 88 | **+3.410 s** | 22:39:15.819 | **+3.409 s** | 22:39:15.825 |

**两份数据的异常出现在同一批样本序号上、同一绝对时刻上（相差 ≤ 9 ms）、Δ 值相差 ≤ 1 ms。** `lp-rr` 里没有 VPP、没有 FRR、没有 sr-agent、没有我们的任何进程 —— 所以这些停顿**不是我们的软件造成的**。90 s 里 3 次，约 30 s 一次。

⚠️ 这条实验的边界要说清楚：`date +%s.%N` 读的是 `CLOCK_REALTIME`，而 −1.4 s 的**倒退**只能是时钟被步进（时间同步在往回校）。所以单看 tick 数据，我**无法区分**"+3.41 s 是容器被冻结了 ~2.4 s" 和 "+3.41 s 是时钟被向前步进"。它证明的是"宿主在动、且两个容器同时动"，不直接证明"包停了"。停包由 (b) 证明。

**(b) 数据面计数器对照：不依赖任何时钟语义**

`dropcorr.py` 每 1 s 采一次 `show interface` + `show errors` + `show bfd sessions`，跑 100 轮 / 每台。VPP 的接口计数器是 VPP 自己的单调计数，跟 `CLOCK_REALTIME` 怎么被校无关：

| | lp-cpe1 | lp-cpe3 |
|---|---|---|
| 采样轮数 | 100 | 100 |
| 出现"某个 wg 口 rx 增量为 0"的轮数 | **12** | **16** |
| 其中所有 wg 口同时 rx=0 | 8 轮（wg1001+wg1002 同时） | 6 轮（三口同时） |
| rx=0 时**同时**至少一条 BFD 会话不是 Up | **9/9、9/9**（逐口） | **10/10、10/10、10/10** |
| 这些轮里 `null-node blackholed packets` 增量合计 | **+80**（12 轮） | **+78**（16 轮，其中 72 个来自 t=61.5–67.5 连续 6 轮各 +12） |

一次 `rx_packets` 增量为 0 都没有出现负数，也没有"rx 涨了但没处理"的情形 —— **口上真的一个包都没收到**。

`corrE.jsonl`（22:24:50 起 150.1 s，四台同采 108 轮）给出更强的共模证据。把每个隧道两端配对（本端 wg 口 rx 增量=0 的时段 vs 对端同口 tx 增量）：

- 全部 **72 段**"本端 rx 冻结"里，**59 段（82%）对端的 tx 在同一时段也几乎不动（≤2 包）**；剩下 13 段全部是每轮事件的**第一段**，对端 tx 增量 3–35 包（正处在"刚停"的边界上）。
- 更重要的是**时刻对齐**：四台、五条隧道上的冻结段聚成四组事件，绝对时间完全一致 —— **t≈0.0–1.7 s、18.4–26.9 s、40.8–46.6 s、137.3–147.1 s**。
- 这四组事件与 `probe/corrE.md` 的丢包窗口**逐一对上**：`2.2s@seq0-10`（0–2 s）、`8.4–9.0s@seq96-140`（19.2–28 s）、`7.0–8.0s@seq201-243`（40.2–48.6 s）、`11.0–11.6s@seq689-749`（137.8–149.8 s）。

**结论（触发源）：这是宿主级的、同时冻结所有容器的停顿，单次持续 1.7–9.8 s（观测到的四组是 1.7 / 8.5 / 5.8 / 9.8 s）。colima VM 的 CPU 抢占或时钟纪律是它的候选解释，但我没有 colima 内部的证据，所以只写到"宿主级、全容器同刻"为止。** 我们的 lab 里有 4 台盒子各占一个 100% busy-poll 的 VPP 线程，8 vCPU 的机器上只剩 4 个 —— 这是这个 lab 的形状，不是产品的形状。

**排除掉的解释，逐条给证据：**

1. **"是我在采样/打流把机器压垮的"（观测者效应）** —— `quiet-60` 那 60 s **一条 CLI 都没跑**，只有六条 ping，仍然 23–25%、仍然六流同刻。
2. **"这台机器一直在抖"** —— `corr2`（20:23:21）60 s watch **六条流 0%**。它不是常态。
3. **"是某条链路/某个隧道口坏了"** —— 同一条隧道的两端在同一秒一起停（上面 82% 那条），且五端同时。
4. **"是 VPP 的 bug"** —— 没有 VPP 的 `lp-rr` 同样停。

**但有一条我自己留下的反证没收口，必须写在这里而不是藏起来。**
诊断工具 `controller/tools/teletiming/main.go`（本轮写的，19:18）的头注释里记着一次更早的实验：**"把 sr-agent `SIGSTOP` 之后同一场景 0% 丢包、零慢样本"**，当时的嫌疑是 sr-agent 每 10 s 的那两条 VPP 二进制 dump（`sr_wg_probe_dump` + `sw_interface_dump`）。如果那条结论成立，那么"宿主冻 3.4 s"本身不足以让流量掉，**还得叠上盒内的遥测 dump** —— 这会改变 §4.3 放大链的定性，也直接改变 P-1/P-2 该先修哪个。
问题是：**那次 SIGSTOP 实验没有任何留档**——`run/loop/` 里既没有对应的 `probe/*.md`，也没有注入时刻（同一类欠账见 D-10、D-12）。所以它现在只是我工具注释里的一句话，不足以推翻 §4.2 那份有文件、有样本序号、有毫秒对齐的对照数据；但也**不能被当作不存在**。已列进 §8.2 的 **R-5**：同一环境跑两遍 60 s watch，一遍 sr-agent 在跑、一遍 `SIGSTOP`，六条流丢包率与 BFD `rx=0` 轮次一起记。

### 4.3 产品侧的放大链：一个 150 ms 的抖动怎么变成 11.6 s 的黑洞

触发源在 lab 宿主，但**客户流量真正断的那 1.0–11.6 s 是我们自己造成的**。逐环都有日志原文，按顺序：

**第 1 环：BFD 检出时间 150 ms，而且没有任何 hold-down。**
`bfd_min_tx_ms=50 / bfd_min_rx_ms=50 / bfd_detect_mult=3` ⇒ `Detection Time (usec) 150000`（每个 BFD dump 里都能看到这一行）。宿主只要停 150 ms，会话就 Down。sr-fib 拿到的就是"不是 Up"，没有 flap damping、没有二次确认、没有宽限期。
实测：`dropcorr` 里 12/16 轮出现 `rx=0`，**这些轮 100% 同时有 BFD 非 Up**（9/9、10/10）。

**第 2 环：会话 Down 之后退到 1 秒发一次，恢复要好几秒。**
这是这一轮测出来的新事实。`z-env2-normal/raw/lp-cpe3--vpp_bfd_sessions.txt` 里 cpe3 那条对 cpe1 的会话（隧道两端状态还互相矛盾：cpe3 说 Down，cpe1 说 Up）：

```text
     0     IPv4 address                               10.250.0.2           10.250.0.1
           Session state                                    Down                 Up
           Diagnostic code                  Control Detection Ti        No Diagnostic
           Detection Time (usec)                          150000
           Desired Min Tx Interval (usec)                  50000                50000
           Transmit interval                             1000000
```

`Desired Min Tx Interval` 仍是 50 ms，但**实际 `Transmit interval` 变成了 1 000 000 µs**。同一次抓表里 cpe1 的 index 1 会话也是 `Transmit interval 1000000` + `Diagnostic code ... Control Detection Ti`。**一次假 Down 之后，这条会话要 1 秒才发一个包；即使对端 50 ms 就活了，本机最快也要 1 s 后才发现。** 11.6 s 的窗口 = 若干个"1 s 退避 + 1 Hz 轮询"串起来。

**第 3 环：sr-fib 1 Hz 轮询，看到"不是 Up"就把这条前缀整条不装。**
`controller/internal/fib/fib.go:306`：

```go
warn("%s: 下一跳 %s 的 BFD 会话不是 Up，该路径跳过", prefix, nh)
```

`poll_sec: 1`（§1.4）。日志原文（cpe1，22:36:43–50 UTC = 22:36–22:38 CST，正好在 `quiet-60` 那个窗口里）：

```text
收敛 tables+0 labels+0/-0 routes+0/-4 mpls-egress=true
收敛 tables+1 … routes+4/-0
警告: 172.16.3.1/32: 下一跳 10.250.0.2 的 BFD 会话不是 Up，该路径跳过; 172.16.4.1/32: 下一跳 10.250.0.4 …
```

**同一条前缀的所有路径都被跳过时，结果不是"降级到备份路径"，是这条前缀在 VPP 里消失。** §3.4 的缺表矩阵（cpe3 的 `172.16.12.1` 两条路径同时被判非 Up → 整个前缀没了）就是这个。

**第 4 环：前缀没了 → 客户流量进 `null-node` / `dpo-drop`。**
`show errors`（cpe1，活设备，两次读之间）：`null-node blackholed 34978→35210`（+232），同窗口 `bfd-udp4-input OK 197040→198345`。`z-env2-normal` 的 cpe1 FIB 里 `10.250.0.2/32`、`10.250.0.4/32` 在 table 0 都是 `dpo-drop` 且 `to:[21014:1597064]`（§3.4）。
`dropcorr` 的量化：在"rx=0 且 BFD 非 Up"的轮里，cpe3 t=61.5–67.5 **连续 6 轮各 +12 个 blackholed**。

**放大比：** 输入是宿主一次 1.7–9.8 s 的停顿（lab 特有），输出是客户侧 1.0–11.6 s 的黑洞、`corrD` 里最长 12.0 s、150 s 内 8–14 次。**注意输出窗口普遍 ≥ 输入窗口** —— 也就是说放大是净增的，BFD 的 1 s 退避 + sr-fib 的 1 Hz + 无 hold-down 这三段纯属我们自己加的。

按 AGENTS.md 第 4 条点名：这条链路上的中断**在生产里同样会发生**，触发条件从"宿主停 3.4 s"换成"客户 WAN 抖 150 ms"即可。150 ms 的抖动在生产 WAN 上不是异常，是常态。

| 编号 | 待拍 | 我的倾向和理由 |
|---|---|---|

### 4.5 顺带撞出来的 G-4：控制台上的遥测数字全是错的

而 overlay 的 /32 只存在于 **table 250**：`controller/internal/agent/dataplane.go:1065`


于是探针每个包都在主表里查 `10.250.0.x` —— 而 §3.4 已经展示主表里那两条正是 `dpo-drop`。**100% 黑洞、`rx=0`、RTT 报"未上报"**，全都是这个。

```go
m.LossPermille = (ProbeLost*1000 + ProbeTx/2) / ProbeTx
```

**没有夹紧到 1000**。窗口 300 ms、超时 900 ms 的组合下，`ProbeLost` 可以大于 `ProbeTx`，算出 >1000‰ 的丢包率给前端。这条我可以直接改（纯 Go、热更路径无关），在报告之后提交。

## 5. 场景 A：站点 12 的主盒 WAN 断了（HA 到底切了什么、没切什么）

证据目录：`capture/a-cpe1wan-down/`（抓于 19:40:11–19:40:28）、`capture/a-cpe1wan-after/`（19:46:56）、
`probe/a-cpe1wan-down.md`（watch 口径，19:40:08 起 55 s，六流同打、间隔 0.2 s）、
`probe/a-cpe1wan-after.md`（snap 口径，19:46:50，六流逐条 20 包 @1.0 s）。
**这两份都属于环境 #1**，也就是 §4 里那个有宿主级停顿的环境；所以本场景里"稳态黑洞"的结论可以用，

### 5.1 注入与恢复的姿势（以及一个证据缺口）

### 5.3 切对了的那一半：overlay 换腿确实发生了

这是本场景唯一的正证：**对端 CPE 在没有任何人工干预、没有配置变更的情况下，把站点 12 的前缀从死的盒子
挪到了活的盒子上**，而且不是"装了但没走过"——`to:[351:29484]` / `to:[371:31164]` 是这条桶的真实转发包数。
机制链在表里能一一对上：

1. `sr-route` 的 RIB 里 `172.16.12.1/32` 有**两条 path**（来自 device 1 和 device 2，同一前缀、同一 RT `65000:1000`），
   这是 O7 Loc-RIB 多路径的结果；断链不会让它少一条，两条都还写着。
2. `sr-fib` 每秒轮一次（`poll_sec: 1`），装配时按 BFD 会话状态过滤：`fib.go:306` 那条"该路径跳过"。
   跳过的是 `10.250.0.1` 这条，剩下的 `10.250.0.7` 照常下发 ⇒ VPP 主表整条替换成 cpe2 那条腿。
3. VPP 装的是 `mpls-label → mpls via 10.250.0.7 wg1006 → stacked-on → host-eth0`，
   所以换腿是**一次整条替换**，不是多桶负载——`buckets:1` 就是证据。

对照 §4：同一套过滤逻辑在"误 Down"时是放大器（把好端端的前缀删掉），在这里是保护器（把死腿摘掉）。
差别只在 BFD 状态判得准不准，不在过滤规则本身——这也是 P-1/P-2 要拍的点。

### 5.4 没切的那一半：VRRP 全程纹丝不动

断链期间和恢复之后，cpe1 的 `vrrp-probe -dump` **逐字相同**，cpe2 也逐字相同：

```text
cpe1  host-eth1 #2 vr1 prio=150 interval=100cs state=MASTER preempt=true ... 跟踪掉0 prio=150 addrs=[10.76.12.10]
cpe2  host-eth2 #2 vr1 prio=100 interval=100cs state=BACKUP preempt=true ... 跟踪掉0 prio=150 addrs=[10.76.12.10]
```

三件事叠在一起决定了"不会切"：

1. **VRRP 实例绑的是客户 LAN 口（host-eth1 / host-eth2 的 LAN 侧），断的是 WAN 口。** LAN 一直 UP，
   通告一直发，MASTER 没有理由让位。这是设计使然，不是 bug。
2. **`跟踪掉0` = 接口跟踪没有生效**（G-3）。VPP 26.06 有跟踪的 API（`vrrp_vr_track_if_add_del`，
   见 `/usr/include/vpp_plugins/vrrp/vrrp.api_types.h`），但我们的 `vppapi/vrrp.go` 只读
   `TrackIfDown`（:106、:360）**没有写路径**；`vrrp_vr_conf` 里也不带跟踪段。
   ⇒ 环境 #1 全部抓表、环境 #2 全部抓表，`跟踪掉0` 一个不差。
   也就是说：即使把 cpe1 的 LAN 口也拔掉，只要 VRRP 自己的口没 down，VIP 也不会漂。
3. 优先级没有掉：`prio=150` 在断链前后一样，`preempt=true` 没有触发任何东西，
   因为没有 BACKUP 观察到更高优先级。

结论：**这一版"HA"在 WAN 故障上只做到了"对端换腿"，没做到"本站换主控"。** 站点侧的出方向流量
（cust12 → 外面）仍然由坏掉的那台接管，而它的 overlay 表是空的。

### 5.5 更糟的那一步：坏盒子还在向客户宣告前缀

cpe1 在 WAN 断掉、VPP 里两条前缀已经不存在的情况下，盒内 FRR 仍然有：

```text
K>* 172.16.3.1/32 [0/0] is directly connected, lo, weight 1, 00:01:08
O   172.16.3.1/32 [110/20] via 10.76.12.12, lcp-x0, weight 1, 01:25:46
K>* 172.16.4.1/32 [0/0] is directly connected, lo, weight 1, 00:01:08
O   172.16.4.1/32 [110/20] via 10.76.12.12, lcp-x0, weight 1, 01:25:38
```

而 cpe1 的 OSPF 配置里有 `redistribute kernel route-map SDWAN2CPE-vpn0`（§3.3），所以这两条 `K`
**正在被当作本站学到的路由播给 cust12**。后果就是上表 cust12 那一行：`172.16.3.1` 依然是
`.11`/`.12` 双下一跳，**WAN 已断的那台仍然分走一半（按流哈希可能是全部）客户出方向流量**，
而它手里那两条前缀在 VPP 里已经不存在了 ⇒ 落进默认 `0.0.0.0/0 dpo-drop`。

一句话概括这个错位：**同一个盒子里，`sr-fib` 认为"这条路没了"（删 VPP 条目），`sr-frr` 认为"这条路还在"
（K 路由留在内核并继续 redistribute）。** 两者都以 `sr-route` 的 RIB 为准，但 RIB 里 path 还在（只是 BFD 不 Up），
于是"有没有路"这个判断在盒内出现了两种答案。§7 的防环讨论会再遇到同一根因。

### 5.9 本场景证明了什么、还欠什么

证明：① overlay 多路径 + BFD 过滤在**对端视角**能自动换腿，且有转发包数佐证；
② 换腿不需要控制面参与（RR 的 path 一条没少）；③ 全程零重启、pid 不变、配置版本号不变。

没证明 / 测不到：① **VIP 切换窗口**——VRRP 没有接口跟踪（G-3），本场景它根本不会动，
要量切换只能再做"把 cpe1 的 LAN 口也拔了"的场景（F，见 §8），那属于必然中断类操作，
预期时长就是 VRRP 自身的 skew/master_adv（100 cs 量级）+ 客户侧 ARP/OSPF 收敛，**本次没测**；
② **cpe1 自己作为转发送的角色丢失后，站点 12 出方向的流量本该由谁接**——现有配置里没有答案，
这是 HA 语义的空洞，不是实现 bug；③ 检测延迟（因为 D-10）。

### 6.3 但是数据面出问题了：cpe1 把两条客户前缀都从客户 LAN 拐回去

`capture/b-del-t3/cpe1.md` 的 `show ip fib`（table 0）：

`10.76.12.12` 是 **cpe2 的客户侧地址**，`host-eth1` 是 cpe1 连客户 LAN 的口。也就是说：

- cpe1 去站点 3 的流量（此时确实没有隧道了）改走客户 LAN，交给 cpe2 —— 这还能算"绕行"；
- cpe1 去站点 4 的流量**本来有一条活着的隧道**（`10.250.0.4`，BFD Up/Up），却也改成了走客户 LAN 交给 cpe2。
  同一次抓表里，**这条 overlay 路径躺在颜色表 10000 里没人用**：
  `172.16.4.1/32 → mpls-label[1000:64:0:eos] → mpls via 10.250.0.4 wg1004`，`to:[0:0]`。

原因要分两条说，而且**第一条不是删除隧道造成的**（这是我在 §7 复核时才查清的，先看 §7.3 的实测时间线）：

- **前一条（早于删除）**：cpe1 的 `K` 路由在场景 A 的恢复窗口里就从 zebra 的 RIB 里消失了（19:47:09 那次抓表，
  `172.16.3.1`、`172.16.4.1` 两条都只剩 `O>* via 10.76.12.12`，`K` 一行都没有；内核路由表里那条 `dev lo` 还在）。
  zebra 不再收得到 K ⇒ 距离 0 的压制消失 ⇒ 客户协议那条上位 ⇒ linux-cp 把它同步进 VPP 主表，
  于是和 sr-fib 的 overlay 路由抢同一个前缀，**赢的是客户侧那条**（VPP 的 source priority，跨源不看
  preference——和 memory 里"OSPF 侧 B 永远优选客户那条"的实测一致）。`172.16.4.1` 的 overlay 路径此时
  仍然活着（RIB 里有、颜色 0、BFD Up，`fib.go:314` 会同时写主表和颜色表），但主表已经被抢。
- **后一条（删除造成的）**：删 t3 ⇒ sr-route 把 dev3 的路径从 RIB 摘掉 ⇒ sr-frr 的**导出计划**里
  `172.16.3.1` 跟着没了 ⇒ 防环护栏（它的唯一输入就是这份导出计划）同时失忆 ⇒ 那条 OSPF 路由被当成
  客户前缀报回 SD-WAN。这一步才是 §6.4 的回灌。

桶计数 `to:[0:0]` 说明这次抓表时新路径还没跑过流量，`172.16.12.1` 的 `to:[1462:122808]` 才是常态。

### 6.7 这个场景的读表口径：sr-fib 的 status 不能当快照用

`loopcheck/b-del-t3.md` 里 cpe4 那一块，`last.routes_removed=0`、`mpls_changed=false`，

`routes_removed` 应该 ≥2（table 0 + 颜色表 10000 各一条）。cpe2 那一块正好是反例：两条 warning（各 1 条路径）
⇒ `routes_removed: 4`、`mpls_changed: true`，数字与逻辑完全吻合。

## 7. 回灌的完整机制链：两个独立条件，缺一个都不成立

§5.5、§6.3、§6.4 各拍到了这条链的一段。这一节把它们拼齐，因为**它不是一个 bug，是两个互不相干的状态
叠在一起才成立的**，而现有那道防环护栏的输入恰好就是其中一个状态本身。

先给结论（下一小节开始逐环给原文）：

> **正常态下这条环就存在于表里，只是"没被选中"。** SD-WAN 学到的前缀以 `K` 路由（距离 0）的形式停在盒子里，
> 客户协议学到的同前缀副本一直躺在 FRR 的 RIB 里没装进 FIB，所以导入侧看不见它。
> **甲**：zebra 把这条 `K` 路由从自己的 RIB 里丢了（内核里还在）⇒ 距离 0 的压制消失 ⇒ 客户那条上位、装进 FIB
> ⇒ 导入侧第一次"看见"它。这一步在 19:47 就发生了，**和删隧道无关**。
> **乙**：sr-frr 的导出计划里也不再包含这个前缀（因为 sr-route 的 RIB 因隧道删除少了这条路径）⇒
> 防环护栏（它唯一的输入就是"我此刻还在导出这个前缀吗"）同时失忆 ⇒ 前缀被当作本站客户前缀报回 SD-WAN。
> 甲单独发生（19:47）：护栏还在，`dropped_loop=2` 一条都没漏出去。甲＋乙（19:51）：护栏漏了 `172.16.3.1`。

### 7.1 正常态：环在表里，只是没被选中

环境 #2 正常态（`capture/z-env2-normal/cpe1.md`，22:08:53）cpe1 的盒内 FRR：

```text
K>* 172.16.3.1/32 [0/0] is directly connected, lo, weight 1, 01:55:29
O   172.16.3.1/32 [110/20] via 10.76.12.12, lcp-x0, weight 1, 01:55:30
K>* 172.16.4.1/32 [0/0] is directly connected, lo, weight 1, 01:55:28
O   172.16.4.1/32 [110/20] via 10.76.12.12, lcp-x0, weight 1, 01:55:29
```

四个字段要分开读：

- `K>* ... [0/0] ... lo`：sr-frr 用 netlink 直接写进内核的 SD-WAN 前缀，出口 `lo`、距离 0，所以它**永远赢**。
  出处 `controller/internal/frr/krt/krt.go:30-36`（VPN0 的出口就是 `lo`），同文件头部的注释把代价写得很清楚：
  「内核认为这些前缀挂在 lo / vpn\<N\> 上。盒子 ip_forward=0……（客户发给这些）前缀的流量会落到 lo —— 这个机制的边界」。
- `O   ` （**没有 `>`、没有 `*`**）：同一个前缀的客户协议副本**一直在 RIB 里**，是 cpe2 通过 cust12 的 OSPF 域发给它的。
  它没被选中、没装进 FIB。
- 它为什么没有变成回灌：观测口径是"未选中的路由不会出现在 `local` 列表里"。
  baseline（18:29）和 b0-clean（19:38:38）两次抓表，cpe1 的 `show ip route` 都是 `K>*`＋`O`（未选中）成对，
  同期 `sr-route status` 的 `local` 只有 `172.16.12.1/32`（§3.2、§6.4 表）；
  而 19:51 一旦 `O>*`（选中）出现，`local` 就多了 `172.16.3.1/32`。
  两个方向的一致证据都在，所以采信"只有被 zebra 选中/装表的那条才会交给导入侧"。
  **但这是从观测反推 zebra 的行为，我没读 FRR 源码证实**（记为 §9 的 D-14）。

`O` 那条为什么必然存在：cpe1 的 running-config 里有 `redistribute kernel route-map SDWAN2CPE-vpn0`（§3.3）。
也就是说 ① 我们把 SD-WAN 前缀发给客户路由器（这是产品要求的行为，客户 LAN 要靠它出方向），
② cust12 把它重新灌进 OSPF area 0，③ cpe1 自己又从 OSPF 学回来。**环在第 ③ 步就已经成型了**，
距离 0 只是把它压在水面下。

### 7.2 两道"防环"分别是什么，为什么一道没挡住

**第一道：sr-frr 的导入侧过滤（`dropped_loop`）。**代码原文，`controller/internal/frr/import.go` 的 `Report`：

```go
		if set := exported[k.VPN]; set != nil {
			if _, loop := set[k.Prefix]; loop {
				stats.LoopDropped++
				continue
			}
		}
```

`exported` 从哪来 —— `cmd/sr-frr/main.go:225`：

```go
// exportedSet is the anti-loop input: what this VPN currently has as K routes.
// Read under the same lock as Apply so a concurrent config change cannot make
// it claim prefixes that were just withdrawn.
```

这四行注释就是整个问题的答案：**护栏的判据是"这个前缀此刻还在我的导出集合里吗"，不是"这个前缀是不是我
曾经导出过的"**。注释里那句"不能让它声称刚刚被撤掉的前缀"说明作者知道这是个易错点，处理方式恰恰是
**让护栏跟着导出集合一起失忆**。于是护栏只在"K 路由还活着"的时候有效；而客户那条能上位的唯一时机，
正是 K 路由没了的时候 —— 两者是同一件事，护栏在需要它的那一瞬间必然不存在。

**第二道：sr-route 的来源过滤（`dropped_own_route`）。**`controller/internal/route/client.go:1369`：

```go
		if rt.DeviceID == c.cfg.DeviceID {
			// The RR must not reflect our own path back; if it does, installing
			// it would make the data plane point our own prefix at a tunnel.
			c.mu.Lock()
			c.counters.ownRoute++
```

它防的是"反射器把我自己发的路又反射回给我"（BGP 标准行为），**和回灌不是同一件事**：
回灌副本携带的身份是 `device_id=1`，对 cpe2/cpe3/cpe4 来说都不是"我自己"，所以这道闸一步都不会跳。
实测：本次所有抓表里四台 cpe 的 `dropped_own_route` **恒为 0**（§3.2 正常态、b-del-t3 故障态都是 0）。

顺带一个必须纠正的读表口径（也写进 §1.5 第 8 条）：**`dropped_loop` 是每轮值不是累计值**
（`cmd/sr-frr/main.go:426` 的 `setPoll` 每轮覆盖）。同一台 cpe1，19:47 读 `2`、19:51 读 `1`，
说明它在那两轮分别挡了 2 条和 1 条 —— 我起草 §6.4 时把它当成累计值，写成"整套测试唯一一次跳过数"，那是错的。

### 7.4 甲：zebra 丢了 K 路由视图，而 sr-frr 永远不会重放（新缺陷 D-11）

19:47:09 这次抓表的三份原文放在一起，就是缺陷本身：

```text
# lp-cpe1--frr_ip_route.txt（zebra 的 RIB）
O>* 172.16.3.1/32 [110/20] via 10.76.12.12, lcp-x0, weight 1, 01:32:27
O>* 172.16.4.1/32 [110/20] via 10.76.12.12, lcp-x0, weight 1, 01:32:19

# lp-cpe1--ip_route.txt（内核路由表，同一个瞬间）
172.16.3.1 dev lo scope link 
172.16.3.1 nhid 10 via 10.76.12.12 dev lcp-x0 proto ospf metric 20 
172.16.4.1 dev lo scope link 
172.16.4.1 nhid 10 via 10.76.12.12 dev lcp-x0 proto ospf metric 20 

# lp-cpe1--sr-frr_status.txt（sr-frr 自己的账本）

```

- 内核里 `dev lo` 那条**在**（sr-frr 写的，它没被删）；
- sr-frr 的账本认为**在**（`injected=2`、`skipped=[]`、`last_error` 空）；
- 但 zebra 的 RIB 里**没有**。⇒ 三者中只有 zebra 的这一份是"客户协议选路"实际用的那一份，
  而它丢了，于是 `O` 上位、进 FIB、被 linux-cp 同步进 VPP 主表（§5.8 表里那一行"下一跳已经不是 overlay"、
  §6.3 那三条 `ipv4 via 10.76.12.12 host-eth1`，根因都在这里，不在删除动作上）。
- **它为什么不会自愈（读码确认，两件事叠起来才是稳态）**：
  `reconcile` 每秒都会调 `Apply`（`controller/cmd/sr-frr/main.go:283`）——**不是**只在签名变化时才下发；
  `planSig` 那段（同文件 `:271`）只管状态文件落盘。但 `Apply` 的差集基准是 sr-frr **自己的账本** `prev`
  （`controller/internal/frr/plan.go:183` 起，`:211` 的 `if old, ok := e.prev[k]; ok { if old == r { next[k]=old; continue } }`）
  ⇒ 账本认为"这条我注过了"就**一个 add 都不发**。再叠加 `f1544e8` 提交说明里的实测结论
  "zebra 对重复 add 不发通知，只有 delete+add 能让它重新学到"——就算发了 add 也救不回来。
  内核里有、账本里有、zebra 里没有，这个三不一致是一个**稳态**，不是一个还没轮到的瞬时。
- 和已修的 #195（`f1544e8` "链路事件后自动重放 K 路由"）的关系，按证据讲：那次的触发集是
  `RTM_DELLINK` / down 的 `RTM_NEWLINK` / `RTM_DELADDR`（`controller/internal/frr/krt/netlink_linux.go`
  的 `WatchLinks`，300 ms 去抖后复用 `touch` 做 delete+add）。§7.3 里 19:39:28 那次 K 行重注
  （19:40:36 看到 `00:01:08`）与这条路径**一致**，说明断链那一拍重放是工作的；
  这次丢的是**恢复之后**那一拍，而 `docker network connect` 产生的是 up/newaddr 事件，不在触发集里
  ⇒ **该修复覆盖不到本情形**。进程 pid 4201 从 19:40 到 19:51 不变，隧道全程健在，所以与重启无关。
- 修复到底在不在跑着的二进制里——23:55 当场实测（环境 #2 仍在跑，容器时钟 UTC）：
  `md5 /usr/local/bin/sr-frr` = `1206236018a177e08f982f5dddc9cc25`，文件时刻 `Nov 2 12:12`（=20:12 CST），
  晚于 `f1544e8` 的提交时刻 11:57 CST；`strings` 命中 `watchLinkEvents` 8 处、`krt.LinkEvent`/`parseLinkEvent` 符号在；
  `/var/log/sr-frr.log`（781 B，止于 20:14:12）里**没有**"链路事件监听没开"那行 ⇒ 监听 socket 起来了。
  ⇒ **环境 #2 的 sr-frr 确实带着这个修复，且重放监听是活的**。
  ⚠️ 而"甲"是在**环境 #1** 上观测到的，那套已在 20:09 拆除、二进制没留档（`loop-bringup.sh:215` 是现场
  `go build`，构建时刻 17:4x CST 理论上含该修复，但我无法证明）⇒ "甲发生在带修复的版本上"这句是**推定**，

- 未定位的部分（诚实边界）：谁在这个窗口里删掉了 zebra 的 K 视图、zebra 为什么没有从内核 netlink 监听里重新收进来，

### 7.5 乙：导出计划缩了一条，护栏在同一拍失忆

19:49:50 的 `DELETE t3` 让 cpe1 的 sr-route RIB 只剩 `172.16.4.1/32`（§6.2 原文）。这条 RIB 变化顺着
`reconcile` 走下去，同时改变了**两件本来该是同一件事的东西**：

1. 导出计划从 2 条缩成 1 条 ⇒ `injected: 1`，内核里 `172.16.3.1` 那条 `dev lo` 被删（该删，SD-WAN 确实没路了）；
2. 护栏的输入就是这份计划（§7.2）⇒ `172.16.3.1` 不再是"我正在导出的前缀"；
3. 而 zebra 那边 `O>* 172.16.3.1` 早就装着（甲，19:47 起就是常态）⇒ 导入侧这一轮**看得见它、且护栏不认识它**
   ⇒ `reported: 2`（`172.16.12.1` ＋ `172.16.3.1`）⇒ sr-route 把它当本地前缀向 RR 宣告。

`dropped_loop: 1` 是这一轮里 `172.16.4.1` 被挡住的记录：同一次事故里，
一条前缀因为计划还包含它而**没**回灌，另一条因为计划缩了而回灌了。这是"护栏只记当下"最直接的对照组。

### 7.6 RR 把这条假路径发给了谁：每一台客户端

O9-a 把 RR 里的隧道邻接闸删了（"标准 RR 就是收到 rr client 的路由发给其他所有"），所以反射不设门槛。
实测确认它确实全发了 —— 三台的 `pending` 原文（`sr-route status`）：

```text
# cpe2（没有到 device 1 的隧道，按你的要求 1↔2 不建）
{"device_id":1,"vrf_id":0,"prefix":"172.16.12.1/32","rts":["65000:1000"],"reason":"no_path"}
{"device_id":1,"vrf_id":0,"prefix":"172.16.3.1/32","rts":["65000:1000"],"reason":"no_path"}   ← 假路径到了

# cpe3（它就是 172.16.3.1 的真正所有者）
{"device_id":1,"vrf_id":0,"prefix":"172.16.12.1/32","rts":["65000:1000"],"reason":"no_path"}
{"device_id":1,"vrf_id":0,"prefix":"172.16.3.1/32","rts":["65000:1000"],"reason":"no_path"}   ← 收到自己前缀的"别人版本"

# cpe4（有到 device 1 的活隧道 ⇒ 直接进 RIB，不进 pending）
rib: 172.16.3.1/32 ←dev1 via 10.250.0.3   /   172.16.3.1/32 ←dev3 via 10.250.0.5
pending: []
```

三条口径说明：

- cpe3 的 `dropped_own_route=0` 是**对的**：假路径带的是 `device_id=1`，不是 3，第二道闸本来就不该跳（§7.2）。
- 假路径在 cpe2/cpe3 那里挂 `no_path`，是因为**收端**没有到 device 1 的隧道 —— 下一跳由收端查自己的隧道表解析，
  这正是"路由不带下一跳"的标准 BGP 递归（见 §1.3 的协议形状）。它不影响宣告本身，RR 照样发。
- cpe1 的 `dropped_no_path=3`、cpe2 的 `=5` 是累计值，和上面的 `pending`（瞬时值）不是同一口径，别拿来对账
  （§1.5 第 8 条、§6.7 是同一类坑）。

### 7.7 挡在 FIB 前面的最后一件事：BFD，而且这次是运气

cpe4 是唯二真的把假路径放进 RIB 的盒子，但它没有把它装进 VPP。原因写在它自己的 `sr-fib status` 里：

```text
"warnings": [
 "172.16.12.1/32: 下一跳 10.250.0.3 的 BFD 会话不是 Up，该路径跳过",
 "172.16.12.1/32: 下一跳 10.250.0.9 的 BFD 会话不是 Up，该路径跳过",
 "172.16.3.1/32: 下一跳 10.250.0.3 的 BFD 会话不是 Up，该路径跳过"
]
```

同一次抓表的 `show bfd sessions`：cpe4 对 `10.250.0.3`（cpe1）的会话 `Session state Down / Up`、
`Transmit interval 1000000`。也就是说 **cpe1↔cpe4 的 BFD 在那一刻是 Down 的**，
`fib.go:306` 顺手把假路径（和真路径一起）跳过了。于是 `172.16.3.1` 在 cpe4 表 0 只剩真腿一条：

```text
172.16.3.1/32
  [@0]: dpo-load-balance: [proto:ip4 index:56 buckets:1 uRPF:52 to:[0:0]]
    [0] [@14]: mpls-label[1000:64:0:eos] → mpls via 10.250.0.5 wg1005
```

**这不是防线，是运气**：这条 BFD Down 属于 §4/#209 那类宿主级停顿，不是本场景注入的（本场景注入的是 1↔3，
和 1↔4 无关）。同一套环境里"两条来源、同一标签 ⇒ 同一个桶 ECMP"是有实证的 —— 19:47:09 的 cpe4：

```text
172.16.12.1/32
  [@0]: dpo-load-balance: [proto:ip4 index:53 buckets:2 uRPF:52 to:[417:35028]]
    [0] mpls via 10.250.0.3 wg1004   （dev1 那条腿）
    [1] mpls via 10.250.0.9 wg1007   （dev2 那条腿）
```

`to:[417:35028]` 表示这个双桶**真的在分担流量**，不是摆设。

**下面是推演，没有实测，标注清楚**：如果抓表那一刻 cpe1↔cpe4 的 BFD 是 Up（正常环境里应该是），
`172.16.3.1` 在 cpe4 表 0 就会变成 dev1＋dev3 的 `buckets:2`，约一半流量被交给 cpe1；
而 cpe1 对这个前缀的下一跳是客户 LAN 上的 cpe2（§6.3、§7.4），于是路径成为
`term3 → cpe4 → cpe1 → cpe2 → cpe3` 的四跳绕行。它不会自愈：cpe1 会持续宣告这条路径（甲是稳态），
而 §6.6 已经证明补建隧道也没能把这条腿拿回来。
它也不是乒乓环 —— cust12 当时对 `172.16.3.1` 只有 `O>* via 10.76.12.12` 一条下一跳，包不会在 1/2 之间来回踢；
但如果再做场景 F（站点 12 两台的 LAN 侧同时出问题），两台都没有 overlay 腿、都指向对方的客户 LAN，
那时决定是绕行还是黑洞的是 cust12 的选路，本实验台里它只有一条 `via 10.76.12.12` ⇒ 结论是**黑洞，不是环**。

### 7.8 客户域里留下的痕迹

同一时刻三台客户侧设备的表（`loopcheck/b-del-t3.md` 第 4 节）：

| 设备 | 与 172.16.3.1 相关的行 | 读法 |
|---|---|---|
| cust12 | `O>* 172.16.3.1/32 [110/20] via 10.76.12.12, eth2` | 客户路由器只剩 cpe2 一条腿（正常）。它把这个前缀又灌回 OSPF area 0 ⇒ 就是 cpe1 那条 `O` 的来源 |
| cpe2 | `K>* 172.16.3.1/32 [0/0] is directly connected, lo` ＋ `K>* 172.16.4.1/32` | **cpe2 的 K 视图没丢**（它没被注入过 WAN 抖动）⇒ 它那边护栏和压制都还在，所以 cpe2 没有回灌 |
| cust4 | `B>* 172.16.3.1/32 [20/0] via 10.76.4.2, eth2` | cpe4 把它从 SD-WAN 学到的前缀发给自己的客户路由器 —— 这是正常导出，不是环；但它说明回灌事件的风波会传进客户 IGP |

cpe2 那一行是这一节里最值钱的一条对照：**同一套代码、同一次删除，K 视图健在的那台没有回灌，
K 视图丢过的那台回灌了。**甲是必要条件，这条对照只有一组样本（n=1），但它是同刻同事件的配对观测。

### 7.9 一件产品里已经存在的缓解：白名单是我自己配宽的

回灌走的第 ⑤ 步有一道硬闸：`Report` 里的 `rule.Allows(k.Prefix)`（prefix-list 白名单）。它没起作用，
因为控制台里是这样配的（`console-log.jsonl` 原文，环境 #2 20:13:42 也重发了一遍）：

```text
POST /api/prefix-lists  {"name":"客户 loopback","entries":[{"prefix":"172.16.0.0/16","le":32}]}
PUT  /api/leak/rows     {"node_id":1,"direction":"to_sdwan","vpn":0,"protocols":["ospf"],"prefix_list":"pl2"}
PUT  /api/leak/rows     {"node_id":2,"direction":"to_sdwan","vpn":0,"protocols":["ospf"],"prefix_list":"pl2"}
PUT  /api/leak/rows     {"node_id":3,"direction":"to_sdwan","vpn":0,"protocols":["bgp"],"prefix_list":"pl2"}
PUT  /api/leak/rows     {"node_id":4,"direction":"to_sdwan","vpn":0,"protocols":["bgp"],"prefix_list":"pl2"}
```

`172.16.0.0/16 le 32` 是"整个 overlay 编址段一把全放"，四台共用同一条 —— 于是 cpe1 有权宣告别人的 `/32`。
如果每台只放行本站前缀（cpe1/2 用 `172.16.12.0/24`、cpe3 用 `172.16.3.0/24`……），
第 ⑤ 步会被 prefix-list 直接挡死，甲再怎么发生都出不了门。

**这条判定要写清楚：这是租户侧配置错误，不是产品缺陷。**但它同时暴露了一个产品问题：
控制台的批量模版/默认给法是"一把全放"，四台共用一条 prefix-list —— 也就是说
**默认配法不提供这个保护**（§11 P-8）。

### 7.10 本节证明了什么、还欠什么

证明（都有原文与时刻）：
1. 回灌的**入口是 administrative distance 的压制消失**，不是任何进程重启、不是配置漂移
   （cpe1 pid 4201 从 19:40 到 19:51 不变，配置版本 v3 不变）；
2. 现有两道防环对回灌**都不起作用**，原因是它们的判据（当前导出集合 / device_id 是否等于自己）
   恰好都不是"这个前缀属于谁"（§7.2 代码原文）；
3. RR 在 O9-a 之后确实把假路径发给了每一台客户端，**真所有者 cpe3 也收到了自己前缀的假副本**；
4. 假路径没进 cpe4 的 FIB 是因为 BFD 恰好 Down（运气），"两条来源同标签 ⇒ 同桶 ECMP"在同环境里有实测；
5. K 视图健在的 cpe2 在同一次删除里没有回灌 —— 甲是必要条件（n=1 的配对观测）。

还欠：
1. 甲的根因（谁删了 zebra 的 K 视图、为什么不再从内核收回来）未定位，需要复现时抓 zebra 日志；
2. "只有被 zebra 选中的路由才会进导入侧"是从两份抓表反推的，没读 FRR 源码证实（D-14）；
3. §7.7 的 ECMP  poisoning 是**推演**，没有实测 —— 要实测就得让 cpe1↔cpe4 的 BFD 保持 Up 再删 t3，
   这属于场景 B 的重跑项（§8.2）；
4. 客户侧 OSPF 的重分发时序（撤一条 K 会不会让客户域出现瞬时黑洞/二次抖动）没有专门的抓表，
   只在 §5.6 的窗口里间接近似到。

### 8.3 "干净基线"到底要什么（三个条件，逐个附实测依据）

§4.2 的结论是宿主级的全容器同时冻结（colima VM 8 vCPU / macOS 16 核；4 台盒子各占一条 VPP 100% busy-poll 主线程，
容器 cgroup `cpu.max = max 100000` 即**没有配额限制**；观测到的四组事件 1.7 / 8.5 / 5.8 / 9.8 s）。
要让 F/G 这类"亚秒级窗口"测量成为可能，下面三条至少满足一条，且**必须写清满足的是哪条**：

1. **一台不做 CPU 超卖的 Linux 宿主**（盒子数不变，仍是 4 台）。
   约束：目前唯一有内核 VRF 的宿主就是这台 colima Ubuntu VM（memory 里那条"lab 已搬 colima"就是为这个），
   真机 `192.168.1.100` 是 arm64 且 2026-11-01 复核仍无内核 VRF。所以这条要你先决定去哪个宿主，我不自己搬。
2. **先把 P-2/P-3 的抖动抑制做进产品**，让 150 ms 级抖动不再进 FIB。
   好处最实在：这样 lab 噪声和生产抖动都测不出"黑洞"，因为黑洞本来就被削掉了；
   代价是**测不到**的那一条恰恰是"没修之前的窗口"，所以必须**先在现在这台机器上量一组前测数字**（已经量了，§4.1/§4.3），修完再量后测。
3. **改判据**：F/G 不测"丢包窗口"，只测"表项到达顺序与状态机"（VRRP 状态、FIB 前缀集合、preference）。
   这条我现在就能做，但**它回答不了你买单的那个问题**（客户流量掉了多久），所以只能当补充，不能替代。

⚠️ 我不会用"多跑几轮取中位数"来糊这条：§4.1 已经证明同一套配置 60 秒里可以 0% 也可以 25%，
事件是离散共模的，中位数没有意义。
