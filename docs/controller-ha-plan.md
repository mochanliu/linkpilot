# 控制器多机 HA 方案

2026-11-14。目标：控制器支持多机 HA。本文是设计，不含实现。
2026-11-14 晚 owner 拍板：**3 台，热切换**（§10-1 已关闭）；台账保留期改为可设置（§10-2 已关闭，当天实现）。

---

## 0. 结论

1. **形态：3 节点对等集群，raft 选主，只有 leader 写，任意节点读。** 不做双活分片，不引入外部数据库。
2. **2 台不算 HA。** 两台没有多数派：要么第三票（一个只投票的常驻进程，容器即可），要么退回"备机 + 人工切换"。这一条必须对销售口径统一，否则交付现场就是"买了两台，倒一台全停"。**已拍板（2026-11-14）：卖 3 台，不做 witness 折中方案。**
3. **热切换是硬要求（owner 2026-11-14）。** 切换必须全自动、无人工介入：leader 挂 → 剩余节点 1–2 s 内选出新主 → 设备不重启、不重新入网，控制台不换地址（VIP 或 DNS 挡在前面）。对应量化指标是 §2 的 RTO ≤ 5 s（选举）+ 设备端点切换 ≤ 30 s（含最坏退避）。要做到这个数，P2 必须把 agent 的"失败退避"改成"换端点立即重试"——退避只对"列表里最后一个地址也失败"生效。
4. **真正的工作量不在 raft，在把状态拆成"硬的"和"软的"。** 现在心跳每拍 `store.Save()` 整份状态（187 KB / 4 台设备 / 每 5 秒），任何共识或数据库实现都会被这个写放大打死。P0 先拆，P1 才上 raft。
5. **提交失败不能回 200。** 现在 `save()` 的错只 `log.Printf`，请求照样成功——磁盘满的时候客户看到的"已发布"其实没落盘。HA 之后这等于"两台各自以为自己是对的"，必须在 P0 一并改成 fail-stop。
6. 设备侧不需要 VIP 也能活：`EnrollResponse.TLSAddrs` 本来就是一个列表，把它扩到心跳响应，agent 自己轮换即可。VIP/DNS 作为部署选项保留，不作为必需品。

## 2. 目标与失效矩阵

| 指标 | 目标 | 依据 |
|---|---|---|
| 配置写 RPO | **0** | "点了发布"必须是已提交；否则切换后设备跑旧配置、控制台显示新配置 |
| 控制面 RTO（选主） | ≤ 5 s | raft election timeout 1–2 s + 新 leader 加载快照；热切换要求全自动 |
| 控制面 RTO（设备回连） | ≤ 30 s（自动） | agent 退避上限 30 s；P2 改成"换端点立即重试"后典型 <2 s |
| 数据面中断 | **0（已实测）** | 控制面不在转发路径（事实 9，2026-11-14 全控制器停机 55 s 实测零丢包） |
| 控制台会话 | 可不保 | 内存会话，切换后重登 |
| 历史（台账） | 允许丢最后一个批次 | 样本是观测，不是账；保留天数已在台账与告警页可设（1–365 天） |

| 故障 | 数据面 | 控制面 | 自愈 |
|---|---|---|---|
| leader 进程死 | 无影响 | 写停 ≤ 选举时间（通常 <2 s），设备 ≤30 s 换端点 | 自动，多数派在即可 |
| follower 死 | 无影响 | 无损（只要还剩 2/3） | 自动；节点回来重新同步 |
| 两台同时死 | 无影响 | **写全停**（没有多数派），读也不可信 | 人工：恢复一台 |
| 网络分区（1 vs 2） | 无影响 | 少数派侧只读且拒写；多数派侧正常 | 自动；旧 leader 降级 |
| 磁盘坏 | 无影响 | 该节点退出集群 | 人工换盘后重新加入 |
| 滚动升级 | 无影响 | 逐个重启不丢写（每次只剩 2/3 仍有多数派） | 自动 |

## 3. 方案对照

| | A. raft 内嵌（**选它**） | B. 共享 Postgres | C. 双活分片 |
|---|---|---|---|
| 外部依赖 | 无 | 数据库（且它自己也要 HA） | 无 |
| 选主 | raft term 自带 | 需要 advisory lock / Patroni | 需要 |
| 2 节点 | 不支持（需第三票） | 不支持（同步备库同样没有多数派） | 不支持 |
| 写语义 | 多数派落盘后提交 | 事务提交 | 分区内本地提交，跨区最终一致 |
| 一体机交付 | 干净（一个二进制） | 要装库、要备份、要升级 | 干净 |
| 改动面 | `Store` 换实现 + 状态分层 | `Store` 换实现 + 状态分层 + 运维 | 重写路由/发现/查询 |
| 适合 | 3 台盒子，客户机房 | 客户已有 PG 集群 | 上千设备、多 Region |
| 工作量 | 中（3–4 周） | 中（2 周）但运维债长期 | 大（2–3 月） |

否决 B 的核心理由：**它把单点从控制器搬到了数据库**。PG 要自动切换同样需要第三个仲裁者（Patroni + etcd，而 etcd 就是 raft），等于绕一圈回到 A，还多背一个数据库的运维和备份。
否决 C 的理由：收益只在"设备数上千、且要求某一个 Region 挂了不影响其它 Region"，当前规模用不上；而代价是把 30k 行里所有假设"一份状态"的地方都改掉。

保留 B 的可能：`Store` 接口留着，将来客户坚持用自家 PG，再加一个 `pgStore` 即可，上层不用动。

## 4. 目标架构

```
                    设备（CPE）                        运维浏览器
                        │                                 │
          ┌─────────────┴──────────┐            ┌─────────┴─────────┐
          │ 端点列表（轮换）        │            │ 统一域名 / VIP     │
          └─────────────┬──────────┘            └─────────┬─────────┘
                        │                                 │
        ┌───────────────┼─────────────────────────────────┼──────────────┐
        │               ▼                                 ▼              │
        │      ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
        │      │  sr-ctrl #1     │  │  sr-ctrl #2     │  │  sr-ctrl #3     │
        │      │  LEADER（写）    │◄─┤  follower（读）  │─►│  follower（读）  │
        │      │  本地 bbolt     │  │  本地 bbolt     │  │  本地 bbolt     │
        │      └────────┬────────┘  └────────┬────────┘  └────────┬────────┘
        │               └──────── raft 日志 / 快照 ────────────────┘
        │                     （多数派落盘才算提交）
        └───────────────────────────────────────────────────────────────┘
             软状态（在线/遥测/观测/告警）走点对点广播，不参与共识
```

四条流，各自的一致性要求不同：

1. **设备写**（enroll/heartbeat/observe/metrics/diag）：heartbeat 的硬部分（密钥绑定、端口补分配、配置版本）进共识；`LastSeen/Config/Tunnel/Ifaces` 是软状态，本地更新 + 广播给同伴，不进 raft。
2. **设备读**（config/bundle、underlay/bundle、watch）：任意节点可服务。都是"版本号驱动 + 收敛"语义，落后一拍无害。watch 由各节点 apply 后推自己的订阅者。
3. **控制台**：任何节点都能打开；**写操作在 follower 上 307 到 leader**。控制台统一走一个域名（VIP 或 DNS），这样 cookie 不会因为换主机而丢。
4. **台账**：审计/事件/告警走共识（量小，必须完整）；`tunnel.sample` 这类高频样本本地落盘 + 广播给同伴，查询时按时间合并去重（`(ts, node_id, serial)` 作键）。

## 5. 状态分层：整个方案的地基

### 5.1 硬状态（进共识，落盘，RPO=0）

| 表 | 为什么必须一致 |
|---|---|
| `nodes` | 身份、序列号、node_id、密钥绑定、端口——两节点各算一份就会同一台设备两个身份 |
| `next_node_id` | 分配器 |
| `tenants` / `accounts` / `claims` | 谁能登录、谁能领设备 |
| `configs` | 设备要拉的配置包（含版本号）——107 KB 的主要来源 |
| `underlays` / `overlays` / `leak_configs` / `rrs` / `sites` / `preauths` | 客户配置 |
| `epoch` | 单调性 |

### 5.2 软状态（不进共识，本地 + 广播）

`LastSeen / Uptime / Config(设备自报) / Tunnel(自报) / Ifaces / obs / tel / alerts / diagRecs / subs / console sessions`。

理由：这些全都是"现在这一刻的事实"，重启或切换后 5 秒内会被设备自己重新报上来。把它们写进共识，等于每次心跳都要一次多数派往返——这正是现在 0.8 次/秒 × 187 KB 的来源。

**失效后的表现要写进产品预期**：切换后最初的 1–2 个心跳周期里，控制台的"在线/应用状态"会显示"未知"，随后自动恢复。这比"两个节点各有一半设备的在线状态"更诚实。

### 5.3 提交规则

- 硬状态改动才提交。处理器在改完之后调用 `commit()`；没有硬改动的心跳**不提交**。
- `commit()` 把整份硬状态按**行**做 diff（每行算 hash，只发变化的行）：一次发布只复制那几行，而不是 107 KB。
- 行级 diff 是 O(n) 扫描。现在 n 很小，代价可忽略；设备数上千时把 `configs` 换成独立键空间（同样不动上层接口）。
- 提交走单一串行队列（长度 1），避免两个处理器同时提交导致快照乱序。
- **提交失败 → 进程退出（fail-stop）**，不是记日志继续。raft 里 leader 落盘失败本来就应该下台；进程退出让设备看到的是连接断开，而不是一个假的 200。

## 6. 一致性语义

| 场景 | 语义 | 说明 |
|---|---|---|
| 写请求落到 follower | 307 到 leader | 设备客户端用的是 `bytes.Reader`，Go 自动跟随 307 并重放 body；**需实测**证书 SAN 是否覆盖目标地址 |
| follower 上的读 | 允许落后（毫秒级） | 控制台显示"集群视图"，可带 `X-Ctrl-Leader` 供排障 |
| 发布后立刻拉配置 | 最终一致 | 设备心跳拿到的版本号可能还是旧的，下一拍收敛，≤5 s |
| watch 事件 | 每节点本地广播 | apply 完才推；不需要跨节点转发，也不会重复推给同一订阅者 |
| 端口/地址分配 | 单写者 | 只有 leader 执行 `underlay.State` 变更，天然不冲突 |
| 控制台会话 | 不复制 | 切换后重登（12 小时会话只在原节点有效） |
| `epoch` | `max(墙钟/60, 已提交值)` | 新 leader 取已提交值兜底，时钟回拨也不会退 |
| 设备证书 | 共享 CA | 三节点同一份 `ca.pem/ca.key`；`server.pem` 首次生成时把三个节点地址 + VIP + 域名全写进 SAN，三节点共用 |
| 控制台证书 | 共享 | 同上，`console-tls/` 目录整体分发，或用 `-console-cert/-console-key` 指向统一证书 |
| STUN 反射器 | 各节点自跑，列表取并集 | 反射是无状态的；leader 死了，设备照样能从别的节点拿到自己的外网映射 |

## 7. 失效剧本

**S1 leader 进程死。**
剩下两台在 election timeout（建议 1–2 s）内选出新 leader → 新 leader 从本地 bbolt 加载已提交状态 → 设备换端点（P2 之后：连接错误立即轮换下一个地址，典型 <2 s；最坏退避 ≤30 s）→ 硬状态零丢失，软状态在 1–2 拍后补齐。**这是热切换的主剧本：全程无人工介入，设备不重启。**

**S2 follower 死。**
无感。写仍要 2/3。节点恢复后 raft 自动补日志；若落后太多则走快照。

**S3 网络分区（1 vs 2）。**
多数派侧继续服务；少数派侧的 leader 在 term 落后后自动降级，拒绝写（返回 503 + `X-Leader`）。**不会出现双主**——这是选 raft 而不是"心跳 + VIP"的主要理由：VIP 方案在分区时会两台都以为自己是主。

**S4 两台同时死。**
写全停，这是物理事实，不是缺陷。产品上要给的是：设备数据面照常转发；控制台给出明确的"集群无多数派"横幅，而不是转圈。

**S5 磁盘坏 / 状态文件损坏。**
该节点拒绝启动（raft 加载失败），集群剩两台继续。换盘后以空节点加入，走快照同步。**禁止**用"空状态启动"顶替——那会用一个空集群覆盖真状态。

**S6 滚动升级。**
逐台停、换二进制、起、等它追上日志，再动下一台。任何时候至少 2/3 在线。比现在的"换件 4 秒断流"更安全。

## 8. 分期与验收

### P0 状态分层（不引入 raft，独立价值）

- `commit()` 替代 `save()`，硬/软分离，心跳不再落盘；提交失败 fail-stop。
- 验收：4 台设备跑 1 小时，`state.json` 的 mtime 只在真实配置变更时变化；`kill -9` 控制器后重启，设备身份/配置/端口不变；模拟磁盘只读，发布请求返回错误而不是 200。

### P1 raft + 三节点

- `raftStore` 实现 `Store`；行级 diff；leader 判定；follower 307；集群加入/移除 CLI。
- 验收：三节点起集群；`kill -9` leader 后 ≤5 s 有新 leader；切换期间 10 次连续发布，最终 10 次都在（RPO=0）；partition 测试（iptables 隔离一台）不出现双主。

### P2 设备侧端点列表

- `HeartbeatResponse` 增加 `TLSAddrs`；agent 保存列表并在失败时轮换；证书 SAN 规划。
- **热切换的关键改动**：换端点不退避——当前地址连接失败（ refused/timeout/TLS 错）立刻试下一个；只有整个列表轮完一轮才走 2s→30s 的退避。否则"热切换"名义上自动，实际要等 30 s。
- 验收：不配 VIP，只给三个地址，拔掉 leader 后设备 ≤30 s 恢复心跳（目标 <2 s）；控制台在任意节点可打开。

### P3 台账与运维

- 审计/事件入共识；样本本地 + 广播；控制台合并查询；`sr-ctrl backup/restore`。
- 验收：切换前后台账时间线连续，无重复无缺口（除故障瞬间）；从任一节点能查到全部历史。

## 附：为什么不是"主备 + VIP"

主备 + VIP（keepalived）是行业里最常见的做法，也是这个方案唯一真正的竞争对手。否决理由只有一条，但很硬：

**分区时两台都会认为自己是主。** keepalived 靠 VRRP 选举，网络一分区，两边各自持有 VIP（或都抢不到），控制器的状态是两份独立的 JSON，谁也不知道对方写了什么。要修就得加仲裁（又是第三票）和 fencing（STONITH，客户机房通常没有可控电源）。既然都要第三票，不如直接用带第三票的共识层——同一个成本，换来的是"写不会分叉"这个更强的保证，以及不再需要 VIP 这个额外组件。
