2026-11-14 晚 owner 拍板：**3 台，热切换**（§11-1 已关闭）；台账保留期改为可设置（§11-2 已关闭，当天实现）。

## 0. 结论

1. **形态：3 节点对等集群，raft 选主，只有 leader 写，任意节点读。** 不做双活分片，不引入外部数据库。
2. **2 台不算 HA。** 两台没有多数派：要么第三票（一个只投票的常驻进程，容器即可），要么退回"备机 + 人工切换"。这一条必须对销售口径统一，否则交付现场就是"买了两台，倒一台全停"。**已拍板（2026-11-14）：卖 3 台，不做 witness 折中方案。**
3. **热切换是硬要求（owner 2026-11-14）。** 切换必须全自动、无人工介入：leader 挂 → 剩余节点 1–2 s 内选出新主 → 设备不重启、不重新入网，控制台不换地址（VIP 或 DNS 挡在前面）。对应量化指标是 §2 的 RTO ≤ 5 s（选举）+ 设备端点切换 ≤ 30 s（含最坏退避）。要做到这个数，P2 必须把 agent 的"失败退避"改成"换端点立即重试"——退避只对"列表里最后一个地址也失败"生效。
4. **真正的工作量不在 raft，在把状态拆成"硬的"和"软的"。** 现在心跳每拍 `store.Save()` 整份状态（187 KB / 4 台设备 / 每 5 秒），任何共识或数据库实现都会被这个写放大打死。P0 先拆，P1 才上 raft。
5. **提交失败不能回 200。** 现在 `save()` 的错只 `log.Printf`，请求照样成功——磁盘满的时候客户看到的"已发布"其实没落盘。HA 之后这等于"两台各自以为自己是对的"，必须在 P0 一并改成 fail-stop。
6. 设备侧不需要 VIP 也能活：`EnrollResponse.TLSAddrs` 本来就是一个列表，把它扩到心跳响应，agent 自己轮换即可。VIP/DNS 作为部署选项保留，不作为必需品。

| 12 | 台账是本地 JSONL，按天一个文件 | `opslog.go:16` | 62 MB / 4 天，今天 28 153 条 `tunnel.sample` 占绝大多数；**这条流不能进共识** |
| 13 | watch 是进程内订阅表，事件由 `broadcastLocked` 推给本地订阅者 | `main.go:2240` | 集群里每个节点 apply 完再推自己的订阅者，不需要跨节点转发 |
| 14 | 端口/overlay 地址/节点 ID 都从 State 里分配 | `underlay/tunnel.go:160`、`main.go` `next_node_id` | 分配器必须只有一个写者，否则两台会发同一个端口 |

状态体积（线上实例）：总计 187 KB，其中 `configs` 107 KB、`nodes` 15.8 KB、`underlays` 3 KB，其余都在 1 KB 量级。
也就是说：**真正的硬状态只有几十 KB，107 KB 是每台设备的配置包**。这决定了 raft 快照很便宜，但也决定了"配置包不能每条命令都整份复制"（见 §5.3）。

## 2. 目标与失效矩阵

| 指标 | 目标 | 依据 |
|---|---|---|
| 配置写 RPO | **0** | "点了发布"必须是已提交；否则切换后设备跑旧配置、控制台显示新配置 |
| 控制面 RTO（选主） | ≤ 5 s | raft election timeout 1–2 s + 新 leader 加载快照；热切换要求全自动 |
| 控制面 RTO（设备回连） | ≤ 30 s（自动） | agent 退避上限 30 s；P2 改成"换端点立即重试"后典型 <2 s |
| 数据面中断 | **0（已实测）** | 控制面不在转发路径（事实 9，2026-11-14 全控制器停机 55 s 实测零丢包） |
| 控制台会话 | 可不保 | 内存会话，切换后重登 |
| 历史（台账） | 允许丢最后一个批次 | 样本是观测，不是账；保留天数已在台账与告警页可设（1–365 天） |

| 故障 | 数据面 | 控制面 | 自愈 |
|---|---|---|---|
| leader 进程死 | 无影响 | 写停 ≤ 选举时间（通常 <2 s），设备 ≤30 s 换端点 | 自动，多数派在即可 |
| follower 死 | 无影响 | 无损（只要还剩 2/3） | 自动；节点回来重新同步 |
| 两台同时死 | 无影响 | **写全停**（没有多数派），读也不可信 | 人工：恢复一台 |
| 网络分区（1 vs 2） | 无影响 | 少数派侧只读且拒写；多数派侧正常 | 自动；旧 leader 降级 |
| 磁盘坏 | 无影响 | 该节点退出集群 | 人工换盘后重新加入 |
| 滚动升级 | 无影响 | 逐个重启不丢写（每次只剩 2/3 仍有多数派） | 自动 |

## 3. 方案对照

| | A. raft 内嵌（**选它**） | B. 共享 Postgres | C. 双活分片 |
|---|---|---|---|
| 外部依赖 | 无 | 数据库（且它自己也要 HA） | 无 |
| 选主 | raft term 自带 | 需要 advisory lock / Patroni | 需要 |
| 2 节点 | 不支持（需第三票） | 不支持（同步备库同样没有多数派） | 不支持 |
| 写语义 | 多数派落盘后提交 | 事务提交 | 分区内本地提交，跨区最终一致 |
| 一体机交付 | 干净（一个二进制） | 要装库、要备份、要升级 | 干净 |
| 改动面 | `Store` 换实现 + 状态分层 | `Store` 换实现 + 状态分层 + 运维 | 重写路由/发现/查询 |
| 适合 | 3 台盒子，客户机房 | 客户已有 PG 集群 | 上千设备、多 Region |
| 工作量 | 中（3–4 周） | 中（2 周）但运维债长期 | 大（2–3 月） |

否决 B 的核心理由：**它把单点从控制器搬到了数据库**。PG 要自动切换同样需要第三个仲裁者（Patroni + etcd，而 etcd 就是 raft），等于绕一圈回到 A，还多背一个数据库的运维和备份。
否决 C 的理由：收益只在"设备数上千、且要求某一个 Region 挂了不影响其它 Region"，当前规模用不上；而代价是把 30k 行里所有假设"一份状态"的地方都改掉。

保留 B 的可能：`Store` 接口留着，将来客户坚持用自家 PG，再加一个 `pgStore` 即可，上层不用动。

## 4. 目标架构

```
                    设备（CPE）                        运维浏览器
                        │                                 │
          ┌─────────────┴──────────┐            ┌─────────┴─────────┐
          │ 端点列表（轮换）        │            │ 统一域名 / VIP     │
          └─────────────┬──────────┘            └─────────┬─────────┘
                        │                                 │
        ┌───────────────┼─────────────────────────────────┼──────────────┐
        │               ▼                                 ▼              │
        │      ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
        │      │  sr-ctrl #1     │  │  sr-ctrl #2     │  │  sr-ctrl #3     │
        │      │  LEADER（写）    │◄─┤  follower（读）  │─►│  follower（读）  │
        │      │  本地 bbolt     │  │  本地 bbolt     │  │  本地 bbolt     │
        │      └────────┬────────┘  └────────┬────────┘  └────────┬────────┘
        │               └──────── raft 日志 / 快照 ────────────────┘
        │                     （多数派落盘才算提交）
        └───────────────────────────────────────────────────────────────┘
             软状态（在线/遥测/观测/告警）走点对点广播，不参与共识
```

四条流，各自的一致性要求不同：

1. **设备写**（enroll/heartbeat/observe/metrics/diag）：heartbeat 的硬部分（密钥绑定、端口补分配、配置版本）进共识；`LastSeen/Config/Tunnel/Ifaces` 是软状态，本地更新 + 广播给同伴，不进 raft。
2. **设备读**（config/bundle、underlay/bundle、watch）：任意节点可服务。都是"版本号驱动 + 收敛"语义，落后一拍无害。watch 由各节点 apply 后推自己的订阅者。
3. **控制台**：任何节点都能打开；**写操作在 follower 上 307 到 leader**。控制台统一走一个域名（VIP 或 DNS），这样 cookie 不会因为换主机而丢。
4. **台账**：审计/事件/告警走共识（量小，必须完整）；`tunnel.sample` 这类高频样本本地落盘 + 广播给同伴，查询时按时间合并去重（`(ts, node_id, serial)` 作键）。

## 5. 状态分层：整个方案的地基

### 5.1 硬状态（进共识，落盘，RPO=0）

| 表 | 为什么必须一致 |
|---|---|
| `nodes` | 身份、序列号、node_id、密钥绑定、端口——两节点各算一份就会同一台设备两个身份 |
| `next_node_id` | 分配器 |
| `tenants` / `accounts` / `claims` | 谁能登录、谁能领设备 |
| `configs` | 设备要拉的配置包（含版本号）——107 KB 的主要来源 |
| `underlays` / `overlays` / `leak_configs` / `rrs` / `sites` / `preauths` | 客户配置 |
| `epoch` | 单调性 |

### 5.2 软状态（不进共识，本地 + 广播）

`LastSeen / Uptime / Config(设备自报) / Tunnel(自报) / Ifaces / obs / tel / alerts / diagRecs / subs / console sessions`。

理由：这些全都是"现在这一刻的事实"，重启或切换后 5 秒内会被设备自己重新报上来。把它们写进共识，等于每次心跳都要一次多数派往返——这正是现在 0.8 次/秒 × 187 KB 的来源。

**失效后的表现要写进产品预期**：切换后最初的 1–2 个心跳周期里，控制台的"在线/应用状态"会显示"未知"，随后自动恢复。这比"两个节点各有一半设备的在线状态"更诚实。

### 5.3 提交规则

- 硬状态改动才提交。处理器在改完之后调用 `commit()`；没有硬改动的心跳**不提交**。
- `commit()` 把整份硬状态按**行**做 diff（每行算 hash，只发变化的行）：一次发布只复制那几行，而不是 107 KB。
- 行级 diff 是 O(n) 扫描。现在 n 很小，代价可忽略；设备数上千时把 `configs` 换成独立键空间（同样不动上层接口）。
- 提交走单一串行队列（长度 1），避免两个处理器同时提交导致快照乱序。
- **提交失败 → 进程退出（fail-stop）**，不是记日志继续。raft 里 leader 落盘失败本来就应该下台；进程退出让设备看到的是连接断开，而不是一个假的 200。

## 6. 一致性语义

| 场景 | 语义 | 说明 |
|---|---|---|
| 写请求落到 follower | 307 到 leader | 设备客户端用的是 `bytes.Reader`，Go 自动跟随 307 并重放 body；**需实测**证书 SAN 是否覆盖目标地址 |
| follower 上的读 | 允许落后（毫秒级） | 控制台显示"集群视图"，可带 `X-Ctrl-Leader` 供排障 |
| 发布后立刻拉配置 | 最终一致 | 设备心跳拿到的版本号可能还是旧的，下一拍收敛，≤5 s |
| watch 事件 | 每节点本地广播 | apply 完才推；不需要跨节点转发，也不会重复推给同一订阅者 |
| 端口/地址分配 | 单写者 | 只有 leader 执行 `underlay.State` 变更，天然不冲突 |
| 控制台会话 | 不复制 | 切换后重登（12 小时会话只在原节点有效） |
| `epoch` | `max(墙钟/60, 已提交值)` | 新 leader 取已提交值兜底，时钟回拨也不会退 |
| 设备证书 | 共享 CA | 三节点同一份 `ca.pem/ca.key`；`server.pem` 首次生成时把三个节点地址 + VIP + 域名全写进 SAN，三节点共用 |
| 控制台证书 | 共享 | 同上，`console-tls/` 目录整体分发，或用 `-console-cert/-console-key` 指向统一证书 |
| STUN 反射器 | 各节点自跑，列表取并集 | 反射是无状态的；leader 死了，设备照样能从别的节点拿到自己的外网映射 |

## 7. 失效剧本

**S1 leader 进程死。**
剩下两台在 election timeout（建议 1–2 s）内选出新 leader → 新 leader 从本地 bbolt 加载已提交状态 → 设备换端点（P2 之后：连接错误立即轮换下一个地址，典型 <2 s；最坏退避 ≤30 s）→ 硬状态零丢失，软状态在 1–2 拍后补齐。**这是热切换的主剧本：全程无人工介入，设备不重启。**

**S2 follower 死。**
无感。写仍要 2/3。节点恢复后 raft 自动补日志；若落后太多则走快照。

**S3 网络分区（1 vs 2）。**
多数派侧继续服务；少数派侧的 leader 在 term 落后后自动降级，拒绝写（返回 503 + `X-Leader`）。**不会出现双主**——这是选 raft 而不是"心跳 + VIP"的主要理由：VIP 方案在分区时会两台都以为自己是主。

**S4 两台同时死。**
写全停，这是物理事实，不是缺陷。产品上要给的是：设备数据面照常转发；控制台给出明确的"集群无多数派"横幅，而不是转圈。

**S5 磁盘坏 / 状态文件损坏。**
该节点拒绝启动（raft 加载失败），集群剩两台继续。换盘后以空节点加入，走快照同步。**禁止**用"空状态启动"顶替——那会用一个空集群覆盖真状态。

**S6 滚动升级。**
逐台停、换二进制、起、等它追上日志，再动下一台。任何时候至少 2/3 在线。比现在的"换件 4 秒断流"更安全。

## 8. 分期与验收

> 落地状态与偏差见 §9。这里保留原始验收口径，**没测过的条目不算打勾**（§9.5 列了哪几条还没测）。

### P0 状态分层（不引入 raft，独立价值）

- `commit()` 替代 `save()`，硬/软分离，心跳不再落盘；提交失败 fail-stop。
- 验收：4 台设备跑 1 小时，`state.json` 的 mtime 只在真实配置变更时变化；`kill -9` 控制器后重启，设备身份/配置/端口不变；模拟磁盘只读，发布请求返回错误而不是 200。

### P1 raft + 三节点

- `raftStore` 实现 `Store`；行级 diff；leader 判定；follower 307；集群加入/移除 CLI。
- 验收：三节点起集群；`kill -9` leader 后 ≤5 s 有新 leader；切换期间 10 次连续发布，最终 10 次都在（RPO=0）；partition 测试（iptables 隔离一台）不出现双主。

### P2 设备侧端点列表

- `HeartbeatResponse` 增加 `TLSAddrs`；agent 保存列表并在失败时轮换；证书 SAN 规划。
- **热切换的关键改动**：换端点不退避——当前地址连接失败（ refused/timeout/TLS 错）立刻试下一个；只有整个列表轮完一轮才走 2s→30s 的退避。否则"热切换"名义上自动，实际要等 30 s。
- 验收：不配 VIP，只给三个地址，拔掉 leader 后设备 ≤30 s 恢复心跳（目标 <2 s）；控制台在任意节点可打开。

### P3 台账与运维

- 审计/事件入共识；样本本地 + 广播；控制台合并查询；`sr-ctrl backup/restore`。
- 验收：切换前后台账时间线连续，无重复无缺口（除故障瞬间）；从任一节点能查到全部历史。

### 9.2 控制台上的四个动作（开启 / 新增 / 替换 / 下线）

客户一开始只有一台，后来上 HA，某台坏了要换，或者发现 4 台用不着 —— 四种场景全部在
「集群」页完成，**没有任何一步需要登后台、改配置文件或重启老节点**。

| 操作 | 控制台动作 | 接口 | 共识层做了什么 | 谁收尾 |
|---|---|---|---|---|
| 开启集群（单机 → 1 台集群） | 「控制器集群」页显示"现在这台控制器是**单机**" → 填本机地址/控制台地址/名称 → 开启集群 | `POST /api/cluster {"action":"init"}` | **不是共识写**：集群还不存在，这一份成员表就是共识的起点 —— 直接写 `state.json`，raft 从 `[self]` 起（单 voter 立刻选自己） | 立刻可用，紧接着就能发加入码 |
| 新增（上 HA，第 2/3 台） | 填名称 + 新机器地址 + 它的控制台地址 → 生成加入码，在新机器上跑一条命令 | `{"action":"token","kind":"add"}` → `PUT /v1/cluster/join` | 加 learner → 追上日志 → 提升 voter | leader 的 sweep（每秒）看 `match+1 >= commit` 连续 3 次就提升 |
| 替换（坏的换掉） | 先点成员行的**替换**（定下目标），再生成加入码 | `{"action":"token","kind":"replace","replace":"c-xxxx"}` | 同新增，另外新成员带 `Replaces` 字段 | sweep：新成员成为 voter 后，自动把旧的标成 `decommissioned`（note="被 X 替换"） |
| 下线（4 台退一台） | 成员行点**下线**、填原因 | `{"action":"remove","id":"c-xxxx"}` | 从 voter/learner 集合里摘掉，状态 `decommissioned`（行不删，审计要留） | 立即生效；剩 2 台仍可写，剩 1 台退化成单点 |

页面顶部有一条**多数派**指示：`有多数派` / `无多数派 · 只读`。掉多数派时控制台整体只读
（写请求在 `commitGuard` 里被拒，不是"看起来成功了其实没落盘"），成员表照旧可看 ——
"我不知道现在能不能改"这件事不该让客户去猜。

加入方只有一条命令（这是"不需要后台部署"的全部含义）：

```bash
sr-ctrl -join https://192.168.1.10:8443 -join-token <控制台生成的码> -node-name ctrl-2
```

加入码是 HMAC-SHA256 签名的短期凭证：里面带集群 id、成员 id、地址、**集群 CA 的 PEM**、
30 分钟过期，且只能用一次 —— 判定方式是"这个成员已经是 active"，不需要额外的已用表
（成员表本身就是那张表；重复使用回 409 `这个加入码已经用过了`）。加入应答回 CA 私钥、
集群密钥、成员表和一份快照 —— 新节点拿到的不是"可以开始了"，而是"已经和集群站在同一页上"。

**为什么必须先 learner 再 voter**：一个空节点直接进 voter 集合，等于把多数派门槛压在
一台还没有日志的机器上；那时候两台活着的机器就凑不出多数派，是自己把自己搞停。
learner 只是接日志、不投票，追上之后再提升，中间没有任何一刻的多数派是虚的。

两条操作边界（都是现场真的会踩的，规则收在 `endpointConflict` 一处，签发与加入两侧共用）：

- **同一地址只允许一个活跃成员。** 两个成员共用一个地址会把多数派算虚：leader 把 append
  发给同一个进程两次，它只认自己那个成员 id，另一份永远追不上 —— 客户看到的是"加了
  一台，一直不变投票成员"。**唯一的例外是替换**：旧机器坏了、新机器直接接管它原来的
  IP，这是常规做法，所以替换目标占着的地址放行。
- **同一台机器重新加入要先清数据目录。** 下线只是把行的状态改成 `decommissioned`
  （审计要留），数据目录里记着的身份还在，拿它去换一个新加入码会被"已经用过了"挡回来。
  清空之后重新加入，硬状态从 leader 的快照重建，不会因此少数据。

### 9.3 与原方案不一样的五处（都是踩出来的）

1. **零第三方依赖 → 自己写 raft。** 原方案 §3 举的是 etcd/raft + bbolt。仓库的规矩是
   不引第三方（§3 那张对照表的最后一行），所以共识层是 stdlib 上手写的 1400 行：
   日志、硬状态、快照都是普通文件 + fsync。代价是要自己把"当前任期规则""双多数派"
   这些边界写对（§9.4 的单测就是给这块的保险）；收益是交叉编译、单二进制、无依赖树。

2. **配置项在 append 时生效，不等提交。** 这条原方案没写，因为看起来不影响正确性 ——
   实际会死。被提升的节点要等到"包含自己的那个配置项被提交"才知道自己有票，而提交
   本身需要多数派；**替换掉老 leader 之后**，新节点还没"知道自己有票"，剩下的人凑不齐
   多数派，集群就停在无主，谁也起不来。现在 leader 侧 `pendingCfg` 立即生效、
   follower 侧在 `handleAppend` 里就把成员表换上，提交只用来推进 `commitIndex`。

3. **leader 也按普通节点应用自己的日志。** 原本有个"跳过自己提的条目"的优化（还带
   回放起点），结果是 leader 的 `state.json` 里没有自己写的东西 —— 它一重启，快照
   （快照就是 `state.json`）里就少了这一截。行是绝对值，重放天然幂等，省这一下没有任何
   收益，只有风险。现在 leader 走和 follower 完全一样的应用路径。

4. **复制热路径上不许拿 `s.mu`。** 写路径会持着 `s.mu` 等多数派应答，而复制又要读
   "成员地址"和"节点间 HTTP client" —— 从 `s.mu` 取就是自锁。现场症状是 leader 冻住、
   所有 append `context deadline exceeded`、然后无限选举。现在成员地址放
   `peerAddr atomic.Pointer`、节点间 client 放 `clusterCli atomic.Pointer`（`main.go`
   里那段注释是留给下一个人的）。

5. **成员变更一次只改一台，且新旧两个多数派都要满足**（`pendingCfg` 记着变更前的集合，
   提交要同时过旧集合和新集合的多数派）。这条原方案写了，落地时确认不能省：滚动升级
   逐台换的时候，一次改两台的窗口里两次变更的多数派会互相踩。

### 9.6 真机 lab：三节点 + 4 台设备（2026-11-14 深夜）

台子：三个 `sr-ctrl` 进程跑在同一台 Mac（192.168.1.4）上，各自 data 目录与端口
（mac-1 8444/8443、mac-2 8544/8543、mac-4 8744/8743 ……），控制台走自签 TLS，
另开一个明文回环口给脚本用；四台 CPE 跑新版 `sr-agent`，`-hb 5`。
量测**只用 Mac 这个钟**（`devpoll.py` 每 300ms 拉三台的 `/api/state`）：设备盒子上的钟和
Mac 差着 8 小时，拿盒子时间戳相减是负的，第一版数据就是这么废掉的。

**切主（`kill -9` 当时是 leader 的 mac-3）**

| 指标 | 实测 | 口径 |
|---|---|---|
| 新 leader 出现 | **+2.24s** | 设计 ≤5s（P1 验收） |
| 设备侧恢复心跳（4 台里最慢） | **+4.93s** | 验收 ≤30s，目标 <2s（P2） |
| 设备侧（最快的那台） | +0.93s | 受 5s 心跳周期限制 |
| 被杀节点采样失败 | 281 次连续 err | 无抖动、无二次选举 |

设备侧那 0.93s 是"心跳失败→立刻换下一个端点"那条规则在起作用（`addrs.go` 里明确不退避）；
最慢的 4.93s 就是"这一拍刚好落在心跳间隙里"，所以**要更快只能缩心跳周期**，
控制面这边已经不再是瓶颈。

**生命周期全流程**（都只经控制台 HTTP 接口，没有后台部署）

| 动作 | 结果 |
|---|---|
| 开启集群（init） | 单机 → 3 台集群，`tls_addrs` 三个地址 |
| 新增（add mac-5） | 入列即 learner，追上（3 个连续 tick）→ voter，约 4s |
| 替换（replace，新机接管 mac-3 的座位） | mac-4 直接成为 voter，**被替换的 mac-3 自动 `decommissioned`**，`tls_addrs` 立刻少一个地址 |
| 下线（remove mac-4） | 从 follower 的控制台发也生效（代理到 leader），剩 2 台仍可写 |

**这一轮改掉的六个问题**（都是只有真机跑起来才会露出来的）

1. **跨节点写被 307 到一个 TLS-only 端口**：跳转按请求的 scheme 拼 `http://`，目标却是
   `-console-tls`。成员记录里加 `console_tls`，scheme 跟着**目标**走。
2. **follower 上的浏览器写不进去（401）**：会话是每进程的，跨源 307 又不带 cookie。
   最终不是补 cookie，而是**把 307 换成服务端代理**（`proxyToLeader`，带 `X-Cluster-Hop`
   防回环、HMAC 的 `X-Cluster-Session` 带身份、剥掉 `Set-Cookie`）——
   浏览器看到的始终是同一个源，登录态不会丢。smoke 里那条断言也跟着改名成
   `write_via_follower`。
3. **健康集群里每台 follower 都喊"无多数派 · 只读"**：`alive` 数的是 `Reachable`，
   而它只有 leader 在维护，follower 上永远数到 1/3。改成 follower 只看"我有没有 leader"。
4. **follower 把活着的 leader 标成"失联"、把所有人标成"落后 43 条"**：`lastHeard` 只在
   leader 收到 append 应答时才写；`matchIndex` 同理。follower 现在在 `handleAppend` 里
   记一笔 leader，视图里第三台报"未知"而不是瞎猜"失联"，只有 leader 才报落后多少。
5. **每台 follower 每 2 秒往日志里刷一行 `commit failed: 这台不是 leader`**：
   `ttlSweeper` 无条件 `save()`。改成 `saveIfLeader()`（这个函数本来就是为这类路径写的）。
   实测改完 12 秒内新增 0 行；leader 空闲时 commit 也不动（diff 为空就不提交）。
6. **空闲集群每秒一次提交**：RR 拉取时间戳原先在硬状态里，拉一次提交一次。
   挪到内存 `rrFetch`（`json:"-"`），实测 12 秒 commit 不动。

脚本都留在 `~/srvmlab/out-ha-lab-20261114/`：`run-cN.sh` 起节点、`failover-run.sh` 做一次
切主量测、`analyze-failover.py` 把采样算成上面那张表、`hapi.py` 是控制台小把手。

### 9.7 两个收口：被下线那台自己退场、重启不再抢主（2026-11-14 深夜，同一天的第二轮）

§9.5 里当时留下的两条边界都不该留给现场，所以当天夜里补掉了。都在同一台 Mac 的
三节点 lab 上验过，`gofmt` / `go vet` / `go test -race` 全绿，容器 smoke 五连过。

**（一）下线是一个完整动作，不是"发条通知，然后记得去那台机器上停进程"**

三层改动，缺一层都不成立：

1. **leader 继续给被摘掉的对端补日志**（`raft.go` 的 `retiring`）——只在它确认收到
   **移除记录本身 + 覆盖该下标的提交点**之后才放手（判据是"那一包 append 带的
   `LeaderCommit`"，不是此刻的 commit；用后者会在并发复制里提前放手，对端就停在
   删除项之前 —— 这正是第一版跑出来的样子）。30s 没回应则放弃，不为一台关机的机器
   永远惦记。
2. **对端自己认账**（`applyEntry`）：应用到一个不含自己的成员表 → `retired`，停参选、
   停复制，回调 `server.retireSelf`。
3. **server 侧的三个动作**：停共识 → 设备侧全部 503（带 `X-Cluster-Leader`，让设备
   按地址表直接跳过去；回 200 才是真正的坑）→ `retireDelay`（10s）后 `os.Exit(0)`。
   加 `-retire-exit=false` 只做前两件。另外**启动时就拒绝**：数据目录里的成员表里
   自己已被标记 `decommissioned` 的话，进程打一行人话就退出，不再"起得来但不在集群里"。

实测（mac-5，`remove` 之后）：

| 观察点 | 结果 |
|---|---|
| 控制台 POST `remove` → 它自己视图 `retired:true` | **0.89s** |
| 设备侧 `POST /v1/config/bundle`（无设备证书） | 下线前 `401` → 下线后 **`503` + `x-cluster-leader: 192.168.1.4:8444`**（1s 内） |
| 4 台真 CPE 的心跳 | 全程 1–3s，**没有人去动它们** |
| 进程 | 10s 后自己退出，端口释放；再起一次 → 打印"已被移出成员表，不再启动"后退出 |

**（二）pre-vote：让"我刚重启"不再等于"换一次主"**

`startElection` 现在先跑一轮预投票（不改 term、不写 meta），拿到多数派"会投你"才真的
翻任期；应答方在 `time.Since(lastAppend) < raftElectionMin` 时一律拒绝（"我这台还听得见
集群，不给你票"）。为此外加了两件事：`handleAppend` 和 leader 自己的 `broadcastAppend`
都要刷新 `lastAppend` —— 只刷 follower 的话，当了 1.2s 主的节点就会开始给落后的重启节点
投赞成票（第一版就是这么错的，测试直接抓住）。

实测：

| 场景 | 改前 | 改后 |
|---|---|---|
| 重启一台 follower | term 13→14，全群重选，约 2s 写空窗 | **term 16→16**，该节点日志里 0 次"发起选举" |
| 重启原来那台 leader（term 17） | 回来就抢主 | **term 17 不变**，以 follower 身份挂回去 |
| `kill -9` 当前 leader | +2.24s | **+2.45s**（多一次预投票往返，term 17→18，单轮即出结果） |

**顺带的两处工程债**（都是这轮才暴出来的）：

- 节点间 RPC 原先用 `context.Background()`，`Stop()` 之后在途请求还会继续发。现在每个
  raft 节点有自己的 ctx，`Stop()` 先取消再等它们退出；顺带把 `broadcastAppend` / 投票
  的 goroutine 纳入 `rpcs` 等待组（测试里"夹具撤了还有人在读时间常量"就是这么来的）。
- `run()` 里先起 applyLoop 再赋值派生 ctx，闭包读的是变量 —— `-race` 直接报。改为先派生
  再起协程。

**测试**：`raft_test.go` 新增三个用例 —— `TestRaftRestartedNodeDoesNotStealLeadership`
（单向静默 + 强制超时，必须一次 term 都不涨）、`TestRaftPreVoteDoesNotBumpTerm`
（预投票不许改 term/leader，而且要等真的收到过心跳再问，否则测的是"集群刚选完主"那个
合法窗口）、`TestRaftRemovedNodeLearnsItWasRemoved`（被摘掉那台必须收到通知、应用移除
记录、不再参选，leader 确认后停止复制）。`cluster-smoke.sh` 第 6 步补了两条断言：
"c4 自己知道被下线了"、"c4 的进程自己退出"。

### 9.8 第三轮收口：stale 可见、台账进共识、CA 私钥退出加入码（2026-11-14 深夜第三轮）

§9.5 剩下的三条边界一次补掉。做法都是业界现成答案（调研过再动手）：
活跃度同步学 Vault HA 的 standby 模型（standby 不评估规则，读数由 active 喂）；
台账进共识学 Vault 的 audit log（single writer，各节点只对自己**亲手服务的**请求记账）；
CA 改造学 kubeadm 的 TLS bootstrap（引导凭据只用来提交申请，私钥永远不出本机，
控制面成员事后经认证通道拿根密钥）。

**（一）last_seen：leader 搭车，不是设备多跑一趟**

设备只跟 leader 心跳，这条不动（动它等于把设备做成三播）。leader 把
`{tenant|node → last_seen}` 表**搭在 append 请求上**发给其余两台（`appendReq.Live`）：
软状态、不进日志、每次 append 都带最新的一份，丢一拍毫无代价。接收侧按**大的算**
（append 可能乱序，旧时间戳不许把新的顶回去），并把换主前留下的 `Stale` 标志翻回来。
follower 不再自己判定失联（ttlSweeper 的 stale/告警/forgetTarget/清遥测全部 leader-only），
控制台显示按 last_seen 年龄推导（`nodeStatusForView`，公式与 sweeper 同一份）。

**（二）台账进共识：leader 单写者，各节点只记自己亲手服务的**

事件/审计行排队（1024 缓冲）→ 每 800ms 或攒满 256 条 `ProposeOps` 一批
（`raftEntry.Ops`，不与设备写混流）→ 多数派提交 → **每台** apply 时写自己的本地 JSONL。
结果：三台台账内容一致，任一节点都能查全部历史；单台磁盘坏了，历史还在另外两台。
配合两条去重规则：转发给 leader 的写请求（`proxyToLeader`）由 leader 记账，请求带
`X-Cluster-Forwarded` 标记，follower 的审计中间件跳过 —— 同一笔写只记一次。
已知取舍：apply 崩溃重放半批会有重复行（人工看的台账，不为此上幂等键）。

**（三）CA：私钥退出加入码（kubeadm 式）**

改前：加入码里塞着 `ca.key`，谁能拿到加入码谁就有根签发权。改后分三步：

1. **加入方本地生成** ed25519 密钥对，join 请求只带公钥（`NodePub`）；
2. leader 用集群 CA **代签** server 证书（SAN：endpoint + 控制台地址）随响应发回 ——
   加入码从此只含公开材料（CA 证书 + 一次性 secret）；
3. leader 在 sweep 里、**提升 voter 之前**，把 CA 私钥（PKCS8）POST 到
   `/v1/cluster/ca`（X-Cluster-Secret 认证）补送给被接纳的节点；接收方先核对
   私钥与本地 `ca.pem` 的公钥一致才落盘。learner 追日志阶段没有私钥也无所谓 ——
   它还不需要签发任何东西。

**（四）这轮踩的最大坑：把 `s.mu` 带回复制热路径**

第一版实现里，leader 的 `sendAppend` 取活跃度表要拿 `s.mu`，而写路径的 `commit()`
正持着 `s.mu` 等多数派（最长 3s）—— 复制 ctx（500ms）整段烧掉，follower 收不到心跳
就发起选举，容器 smoke 里 term 一路爬到 64、偶发全绿偶发风暴。这正是 §9.3 立过的
规矩（**复制热路径上不许拿 `s.mu`**）被自己亲手违反。修法两条都无锁：

- 发送侧：快照放 `atomic.Pointer`（`liveSnap`），ttlSweeper 每 2s 持锁重建一次，
  sendAppend 只读指针；
- 接收侧：handleAppend 应答路径只做一次**非阻塞**投递（队列满即丢），
  真正合并进软状态由独立的 `liveApplier` 协程持锁做 —— append 应答晚一拍，
  leader 的复制 ctx 又要烧。

修完的验收数字：容器 smoke **4 连过**，全程选举 2 次（单机自选 term=1 +
kill -9 后的正常重选 term=2），**max term=2**（风暴版本是 64）；新成员 c4 的日志里
"集群 CA 私钥已补送 → 已收到，签发能力就绪"先于 voter 提升；`go test -race` 全绿。

**测试**：`raft_test.go` 新增 `TestRaftOpsReplicated`（三节点 ProposeOps 有序到达）、
`TestRaftLivenessPiggyback`（两台 follower 都收到搭车表）、`TestApplyLivenessMaxWins`
（乱序旧包不许覆盖）；新增 `cluster_ca_test.go`（私钥匹配才收、外来的密钥拒收、
无 secret 拒绝、被转发的请求审计不重复记账）。

**真机 lab 重部署验证（2026-11-15，sr-ctrl.lab7）**：三节点滚动换件
（follower → follower → leader），备份在 `data.prev-cluster-20261115` / `c2.prev-lab6` /
`c6.prev-lab6`。结果：

| 验收点 | 改前（lab6） | 改后（lab7） |
|---|---|---|
| follower 控制台的设备 last_seen | 30,269s 前（≈8.4h 前，全是旧的） | **4 台 CPE 全部 fresh（0–5s）**，三台一致 |
| 台账复制 | 各节点只有自己的 | 连续行三台逐字节一致（c2↔c6 tail 逐行相同） |
| leader 重启 | —— | mac-2 重启 → mac-6 当了 ~9s leader（term 20）→ mac-1 接任（term 21），quorum 全程在，4 台 CPE 心跳没断 |

两个**如实记录的残余**（都不是缺陷，是设计里写明的取舍）：

- 换主窗口的台账行：term 20 那位 leader 排队的行没来得及提交就丢了主，
  opsShipper 的兜底把它写进了**本机**文件 —— 这 7 行只在那一台上（丢了主但没丢历史，
  代价是三台在选举窗口附近不逐字节一致）。
- follower 自己亲手服务的请求（如本机控制台登录）的 audit 行按 Vault 式规则只落本机。

## 附：为什么不是"主备 + VIP"

主备 + VIP（keepalived）是行业里最常见的做法，也是这个方案唯一真正的竞争对手。否决理由只有一条，但很硬：

**分区时两台都会认为自己是主。** keepalived 靠 VRRP 选举，网络一分区，两边各自持有 VIP（或都抢不到），控制器的状态是两份独立的 JSON，谁也不知道对方写了什么。要修就得加仲裁（又是第三票）和 fencing（STONITH，客户机房通常没有可控电源）。既然都要第三票，不如直接用带第三票的共识层——同一个成本，换来的是"写不会分叉"这个更强的保证，以及不再需要 VIP 这个额外组件。
