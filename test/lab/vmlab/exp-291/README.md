# exp-291 —— 动态策略（第 2 项需求）VM 台端到端验证

日期：2026-11-10/11 · 分支 `feat/vbond-control-plane` · 提交 `7a1c7fa`（功能）+ `b7c2bc8`（文案修复）

## 结论

动态策略全链路在 4-CPE VM 台上跑通：

```
控制台动态行（对端 #3 · 候选 2,3 · 延迟≤50ms 抖动≤20ms 丢包≤200‰）
  → 第 7 段渲染 selector_table=10001（公式 10000+rowID）
  → sr-apply 建 ABF→10001 + 种 0.0.0.0/0→主表
  → sr-agent 内 sla.Selector 每秒读探针、选最优颜色
  → 一次 ip_route_add_del 把 10001 的默认路由指向颜色表
  → ABF/ACL 原封不动
```

## 实测记录

| 项 | 结果 |
|---|---|
| 端到端（`cust12 -I 172.16.12.1 → 172.16.3.1`） | 双向 5/5、0% 丢包 |
| 颜色切换 t9: 2→3 | 1 拍内完成；10001 deag `ipv4-VRF:2000` → `ipv4-VRF:3000`；颜色表 2000 清空、3000 收 2 条（对端 3 经 wg1009、对端 4 经 wg1010）；流量 5/5 |
| 回切 t9: 3→2 | 同样 1 拍内；流量 5/5 |
| 控制台实时视图 | `current_color`、Match「动态 → 对端 #3 · 候选 2, 3 · … · 当前颜色 N」均随上报刷新 |
| 选路理由文案 | 三种来路分别验证：「首次选择」「当前颜色 N 已不在候选隧道里（候选：M），按 SLA 重选」「当前颜色不再达标…」 |
| 单元测试 | sla/apply/fib 全绿（含迟滞、100% 丢包立即切、VPP 重启恢复路由、无候选保持） |

切换原因（agent 日志）：

```
sla: 行 1 → 颜色 3（当前颜色 2 已不在候选隧道里（候选：3），按 SLA 重选：颜色 3（延迟 3.4ms，抖动 1.8ms，丢包 0‰，…））
sla: 行 1 → 颜色 2（首次选择：颜色 2（延迟 5.3ms，抖动 2.6ms，丢包 0‰，…））
```

## 已知约束

1. **一设备对一隧道（M-3 门禁）**：`POST /api/underlay/tunnels` 拒绝同设备对第二条隧道，
   所以今天"一个对端只能有一个颜色"。多颜色竞争同一对端（真正的 SLA 择优切换）
   要等 M-3（每设备 8 把密钥）或双 WAN 硬件。本轮用"改 t9 的颜色"验证切换机制，
   决策语义本身（迟滞、最接近、立即切）由单元测试覆盖。
2. **探针按隧道不按对端聚合**：一个 wg 接口 = 一个颜色隧道，每颜色取"该颜色最好一条"。
3. selector_table 行号上限 999（10001..10999），颜色表最大 7255，两段不重叠。

## 追加：preempt 复选框（owner 2026-11-11，提交 685f819）

动态行加"抢占"开关，**默认不勾**：

- 不勾（粘住）：当前隧道还达标就一直用，别的隧道更优也不切；直到它不达标且
  **有**达标候选可用才切。切换理由："保持颜色 N（未勾抢占：仍达标 …；颜色 M 更优但不抢占）"。
- 勾（抢占）：永远追当前 SLA 最优的一条（沿用迟滞：更优者连续 3 拍胜出才切）。

注意"粘住"粘的是**达标期间不被抢**，不是"死了也不走"：当前 100% 丢包立即切、
颜色被配置挤掉立即重选、全不达标走最接近——两种模式一致。

VM 台 v18/v19 双向发布验证：勾选 → `store/current/policy.json:"preempt": true`；
取消 → 键消失（omitempty，不勾时渲染字节与老版本一致）。端到端流量不受影响。
决策语义（粘住不被抢 + 不达标立即切）由 `TestStickyKeepsEligibleCurrentUntilItFailsSLA` 覆盖；
Lab 里只有单颜色/对端，追最优场景跑不出来，靠单测。

遗留伤：磁盘满事故中 start.sh 曾连打三条 "sr-apply: Permission denied"
（01:02 换 agent 时窗口期的暂时现象，之后自愈，非权限问题——bin 是 0755 且可直接执行）。

## 本次踩坑（运维纪律）

1. **2.4G 磁盘满**：install-291 时 CPE1/3/4 `No space left on device`，二进制被截成 0 字节，
   sr-box-watch `start.sh up` 失败、盒子上无进程。恢复：`journalctl --vacuum-size=20M`、
   `apt-get clean`、`rm -rf /root/vmlab/in* /var/crash/*`。**install 脚本应预检剩余空间**（待办）。
2. **杀 sr-ctrl 连带杀了 sr-rr**：旧 sr-ctrl 与两个 rr 同在一个后台任务进程组，
   杀 ctrl 把 rr 一起带走 → 全部 CPE RIB 空、颜色表只剩兜底 → 全断。
   RR 要像 ctrl 一样用常驻任务各自拉起，恢复后 `rib_ready=true` 秒级收敛。
3. **`pkill -f "sr-agent -ctrl"` 自杀**：远程 shell 的 argv 里就有这个串，pkill 把
   ssh 会话自己杀了。盒子上杀进程用 `pkill -x`。
4. **裸 ping 不代表业务通**（exp-290 §3.1 重演）：`cust12 ping 172.16.3.1` 源地址是客户口
   172.31.12.13，对端没有回它的路由，100% 丢包但策略链路是好的。端到端验证必须
   `ping -I 172.16.12.1`。
5. **scp 单连接到 CPE 不可靠**（~13.7KB/s 且会被中断截断）：9.8MB 的 sr-agent 两次
   scp 全部 sha 不符/超时。沿用 push-par.sh 分块并行 + sha 核验，一次过。
