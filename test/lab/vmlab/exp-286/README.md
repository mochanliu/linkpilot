## 0. 一页结论

1. **lab 的基线不干净，但不是报告里写的那条原因。** 四台盒子的 BFD 在没有注入任何故障时
   自发抖动：CPE2 **302 次/11.3h**、CPE3 **536 次/13.2h**、CPE4 **511 次/10.9h**（约 1.3–2.2 分钟一次，
   每次 ~1s 恢复）。客户侧 131 秒实测丢 **1.08%**。任何亚秒级切换的读数都必须扣掉这个底噪。

2. **部署漂移：`sr-agent` 四台都没有 #275。** `sr-route` 二进制里有 `PUT /tunnel-state` 处理器
   （`grep -a` 命中 1 次、非法 body 返回 400、未知路径返回 404），`sr-agent` 里 `tunnel-state`
   命中 **0 次**，抓包 25 秒**一条 PUT 都没有**，日志里也没有 `route-state pusher`。
   所以「BFD 说死的路不参与选优」这条链在 lab 上**没有生效**——`rib` 里的路由一直留着，
   与仓库 HEAD 的代码意图不一致。

3. **链①（本机口 down）复测通过，而且比 #285 的分辨率更硬：**
   CPE3 的 `wg1009` down 的**同一个采样点**里，`resolved` 2→1、承载下一跳从 10.250.0.0 切到
   10.250.0.6，而 `len` 仍是 2、BFD 仍显示 **Up**；**155 ms 后** BFD 才转 Down、sr-fib 才把死路径删掉。
   客户侧 **0/600 丢包**。这是「VPP 原生先回落、BFD 后到」的直接证据。

4. **链②（只有对端死）复测通过：** CPE1 的口 down 后本机 BFD **131 ms** 转 Down；
   CPE3 在同一采样点内删掉 `pref=10`、承载切到 `pref=12`；客户侧 **1/600 丢包**（50 ms 量级）。

5. **ECMP 形状（CPE4，两条等价腿）切换代价 3/600 丢包（~150 ms）**，`len 2→1 / buckets 2→1`
   在一个采样点内完成。恢复后 **8.4 秒**又自发抖动了一次（无注入），再次摘路。

6. **整条隧道断（CPE4 的 t14）在 CPE2 侧：FIB 一个采样点内消失**，并**回落到 `0.0.0.0/0`**
   （`pref=20,0`、无 `mpls via`）——这正是「精确行被删时打印覆盖它的那条」的坑；
   客户 **144/600 丢包（24%）**，整个 20 秒窗口全黑。`rib` 一动不动（原因见第 2 条）。

7. **负载均衡量出来了：** CPE4 的 300 条**独立五元组**按 **156/138（53%/47%）** 分到两条隧道；
   同样 300 发但**同一个源端口**则 **100% 走同一条（0/300）** ⇒ 逐流哈希，不是逐包。
   CPE3 主备形状下 300 发 **全部走主路（296/0）**，备路一条不承载。

8. **环路：今天没有环，但防线只有一张 prefix-list。** 站点 12 的两台盒子**各自**把远端前缀
   （172.16.3.1/172.16.4.1）重分发进了 OSPF，CPE1 的 OSPF 库里能看到**每个前缀两条外部 LSA**；
   cust12 已经按 ECMP 学这两条。CPE2 之所以没有把它再送回 SD-WAN，唯一原因是它的导入表是
   `172.16.12.1/32`。**控制台预置的另一张表（pl2「客户 loopback」）是 `172.16.0.0/16 le 32`**，
   站点 12 一旦改用它，就会形成重注入。这一条需要一个控制台改动才能实测，见 §7。

9. **`vm-verify.sh` 本轮 396 PASS / 0 FAIL / 2 WARN**，不是文档里的 398/0/0。
   差的 2 条是 §9 客户 ping 撞上了第 1 条的抖动窗口（20% 丢包 + 同窗口摘路 5–13 条），
   属于「同一颗子弹打两次的相位不同」，不是形状回归。

### 1.4 本轮新踩的坑（都付了时间）

1. **盒内没有 `strings`**（`which strings` 为空）——用它判「二进制有没有某功能」会静默得到 0。
2. **`show bfd sessions` 的 `Last control frame … ago` 是坏字段**：读数是 `368380s ago` 且
   每次采样都跟着墙钟一起长；但同一时刻 `bfd-udp4-input` 每 3 秒涨 198 个（3 条会话 × 20/s），
   说明 BFD 报文一直在走。**判活只能用会话状态或 `bfd-udp4-input` 差分**。
3. **Mac 的 BSD `date` 没有 `%N`**（`+%s%3N` 会输出字面 N），计时脚本要用 python 取毫秒。
4. **客户 VM 会被宿主拖慢**：一次 `ping -c 600 -i 0.05` 的计划时长 30 s，实际跑了 **69 s**。
   所以「丢了几发」可信，「窗口多少毫秒」不可信；窗口要用 `-D` 的收发时间戳量。
5. 整表 dump 没有 `path:`/`pref`/`buckets`，只能单前缀查（老坑，§7.15）。
6. 精确行被删会打印 LPM 覆盖项（`pref=20,0`），不是「没有」（老坑，§7.16）。
7. **盒间时钟互差几十分钟**：本轮实测 CPE3 比 CPE1 慢 **48.2 分钟**。跨机只能比时长。

### 2.3 BFD 自发抖动（本轮最重要的基线事实）

无注入、无脚本运行时，`fib.log` 里 `BFD x -> down` 的累计：

| 盒子 | 次数 | 统计区间（盒内时钟） | 折合 |
| --- | --- | --- | --- |
| CPE2 | 302 | 02:32 → 13:51（11.3h） | ~27 次/h |
| CPE3 | 536 | 00:26 → 13:37（13.2h） | ~41 次/h |
| CPE4 | 511 | 11:05 → 21:59（10.9h） | ~47 次/h |
| CPE1 | 0 | — | **老 sr-fib，不订阅 BFD 事件，不算** |

典型形状（CPE4，21:45）：

```
21:45:00 BFD 10.250.0.4 -> down   → 收敛 routes+0/-1
21:45:00 BFD 10.250.0.4 -> init
21:45:01 BFD 10.250.0.4 -> up     → 收敛 routes+1/-0
```

每次抖动 = 摘路 → ~1s 后装回；客户侧连续 131 秒实测丢 **13/1200（1.08%）**。
抖动是**阵发**的（有一段 60 秒窗口内零次），不是均匀分布。

怀疑方向：50 ms × detect_mult 3 = **150 ms 的检测时间**，对 VirtualBox 里的 VPP 太紧，
宿主一次调度抖动就够。本轮**没有**做宿主侧的证据（没采 Mac 的 load/freeze），
所以只能说「与宿主调度相关」是假设，不是结论。

## 3. 故障链复测（四枪）

注入一律是 `vppctl "set interface state <if> down"`，保持 20 s 再 `up`，单发不循环。
`Δif` = 相对**该盒自己**的接口 down 时刻（同一时钟，可精确到采样分辨率）。

### S1：链②，只有对端死（CPE1 的 wg1009 down，被测 CPE3）

| 观测点 | 读数 |
| --- | --- |
| CPE1 本机 | if down → BFD Down **+131 ms**；恢复后 BFD Up **+172 ms** |
| CPE3 FIB | 同一采样点：`len 2→1`、`prefs 10,12→12`、`carry 10.250.0.0→10.250.0.6`、BFD 10.250.0.0 Down |
| 客户 cust3→172.16.12.1 | **599/600 收到，丢 1 发**（seq 7） |

### S2：链①，本机口 down（CPE3 自己的 wg1009）

这一枪是**顺序**的关键证据：

| Δif | 读数 |
| --- | --- |
| **0 ms** | `resolved 2→1`，`carry 10.250.0.0→10.250.0.6`，`if=down`；但 **`len` 仍 2、`prefs` 仍 10,12、BFD 仍 Up** |
| **+155 ms** | BFD 10.250.0.0 **Down**；同一拍 `len 2→1`、`prefs→12` |
| +22.4 s | 口 up |
| +23.1 s | BFD Up、`len 1→2`、承载回到 10.250.0.0 |
| 客户 | **600/600，0 丢包** |

结论：口 down 的那一刻 VPP 已经把该 path 标非 resolved 并把 DPO 桶切到备份腿，
**BFD 晚 155 ms 才反应过来**；sr-fib 随后删路径对转发没有影响（只是把死腿从行里清掉）。

### S3：ECMP 形状（CPE1 的 wg1010 down，被测 CPE4）

| 观测点 | 读数 |
| --- | --- |
| CPE1 本机 | BFD Down +159 ms |
| CPE4 FIB | 同一采样点：`len 2→1`、`buckets 2→1`、`carry {.2,.8}→{.8}` |
| 客户 cust4→172.16.12.1 | **597/600，丢 3 发（~150 ms）** |
| 恢复 | +25.2 s `len 1→2 / buckets 1→2` |
| **+33.7 s** | **无注入又自发抖了一次**（BFD .2 Down → 摘路），+34.7 s 装回 |

### S4：整条隧道断（CPE4 的 t14 down，被测 CPE2，你最早问的那个场景）

| 观测点 | 读数 |
| --- | --- |
| CPE2 FIB | 同一采样点：`len 1→0`，`prefs 10→20,0`，`carry 10.250.0.9→none` |
| 说明 | 这是**精确行被删后回落到 `0.0.0.0/0`**，不是「行里还剩两条」 |

## 4. 站点 HA 与负载均衡

站点 12 的两台盒子（CPE1/CPE2）同时宣告 `172.16.12.1/32`，因此 CPE3/CPE4 各有两条腿。

| 场景 | 腿 A | 腿 B | 结论 |

## 5. 环路

### 5.1 今天没有环，但「同站双盒」已经把环路的前置条件摆好了

- CPE1 与 CPE2 都在把远端前缀重分发进 OSPF（`redistribute kernel route-map SDWAN2CPE-vpn0`，
  route-map 是空 permit）。
- 结果：**CPE1 的 OSPF 外部 LSA 库里，172.16.3.1 和 172.16.4.1 各有两条**（两个发起者）。
- `cust12` 看到的是 OSPF ECMP：

```
172.16.3.1/32  ospf distance 110 metric 20
  * 172.31.12.1 via enp0s8   ← CPE1
  * 172.31.12.2 via enp0s8   ← CPE2
```

- CPE2 自己也有这条内核路由（`172.16.3.1 dev lo scope link`，sr-frr 注入的 K 路由），
  但因为导入 prefix-list 是 `172.16.12.1/32`，它**只报自己的 1 条**（`reported=1 injected=2`）。

### 5.2 防线是什么、有多脆

防线**只有一张接口级 prefix-list**（`/etc/sr-frr.json` 的 `import_rules.prefixes`）：

| 盒子 | 导入来源 | 表 | 覆盖 |
| --- | --- | --- | --- |
| CPE1/CPE2 | ospf | `172.16.12.1/32` | 只放自己的客户前缀 |
| CPE3/CPE4 | bgp | `172.16.0.0/16 le 32` | 放整个 /16 |

控制台里预置了两张表：`pl2「客户 loopback」= 172.16.0.0/16 le 32`、`pl3「本站客户前缀」= 172.16.12.1/32`。
**站点 12 用的是 pl3，恰好是唯一能挡住重注入的那张。** 如果按 CPE3/CPE4 的写法换成 pl2，
CPE2 就会把从 OSPF 学到的 172.16.3.1 当成自己的客户前缀重新宣告回 SD-WAN。

这不是理论推演：CPE3 现在就是这个写法（bgp + /16），只是 eBGP 的水平分割挡住了回灌；
站点 12 用的是 OSPF，**没有水平分割**，只有这张表。

### 5.3 顺手撞到的一条：zebra 里同前缀有多条 kernel 条目

CPE2 上 `show ip route 172.16.3.1` 打印 **5 条 protocol=kernel、nexthop 全是 lo** 的条目
（`Last update` 从 10 分钟前到 3 天前不等），内核表里实际只有 1 条。
60 秒空闲窗口里没有增长（那段时间也没有抖动），所以**不确定是否随每次重注入累积**；
但它说明 sr-frr 注入的删除/替换在某条路径上没有真正生效，值得单独开一条。
