# exp-290：静态策略第一次端到端跑通（VM 台），外加两个产品缺陷与三个测量陷阱

日期：2026-11-10（CST）。
对象：VirtualBox 四台 CPE（CPE1–4）+ Mac 侧控制面（sr-ctrl / 双 sr-rr）。
本轮做的是**静态策略（需求第 1 项）在真实 VRF 环境下的第一次端到端验证**。

Docker 实验台（`test/lab/loop-*`）在这一轮被放弃了：它不支持 VRF，而静态策略的
落点就是"每 VRF 每颜色一张 FIB 表"，没有 VRF 这一层，测到的只是一个特例。所以全部
结论都来自 VM 台。

## 0. 结论

- 静态策略整条链路（控制台一页 → 配置包第 7 段 → 盒子 ACL+ABF → 彩表 → MPLS 隧道）
  **双向通**：`cust12 → 172.16.3.1` 与 `cust3 → 172.16.12.1` 各 5/5、0% 丢包。
- 幂等、改前缀、换颜色、删行、VPP 重启重放，五种变更全部按设计表现。
- 路上挖出**两个产品缺陷**（都已修，见 §2）和**三个测量陷阱**（见 §3）——
  后者一度让我把"策略没生效"当成数据面问题查了很久。

## 2. 两个产品缺陷

### 2.1 ACL 索引 0 被当成"没填"

VPP 给第一张 ACL 分配的索引就是 0。库内部把 0 当"新建、索引由你分配"的哨兵，
于是"建好了 ACL"和"没有 ACL"在返回值上无法区分。首次下发直接死在
`ABF 策略 1001 需要一个 ACL index`，而 `show acl-plugin acl` 明明打着
`acl-index 0 tag {sr-pol-1}`。

隐藏的第二种坏法更麻烦：替换 0 号 ACL 被改写成"新建"，每轮对账多一张 ACL，
索引一路涨、旧的留着 —— 看着"原地替换不 churn"，实际一直在漏。

修法：独立标记 `ACLNew = ^uint32(0)`；`ACLAddReplace` 把 index 原样发下去；
ABF 侧去掉 `ACLIndex == 0` 的拒绝；对账改看 `tagIndex` 的 `exists` 而不是 `idx == 0`。
回归测试 `TestPolicyFirstRowUsesACLIndexZero` / `TestPolicyReplacesIndexZeroACLInPlace`。

### 2.2 `show interface` 的 `tx-error` 计数器被当成命令失败

这条是本轮最贵的一个：**配置发布成功、设备回执应用成功，但策略一条都没下发。**

`vppctl` 失败时也 exit 0，所以 `vppError` 靠输出里的关键字判错。旧实现整段输出里找
`error`，而 `show interface` 有一行计数器就叫 `tx-error`。CPE2 的客户口有过 3 次
tx error，于是：

```
sr-apply: vppctl show interface host-enp0s8: Name  Idx  State  MTU (...)  Counter  Count
host-enp0s8   1  up  1500/0/0/0  rx packets  6928
                                  ...
                                  tx-error       3
```

`vppIfaceExists` 把它判成"读接口失败"，apply 在第 1 段中止；apply 是 `err != nil`
就短路，于是 route / policy / VRRP 三段一个都没跑。设备回执里的 error 字段就是那张
计数表本身，看不出跟 tx 计数有任何关系。

CPE4（`tx-error 1`）同样每次都停在这里，只是它没配策略，所以一直没人发现 ——
**它的 overlay 路由推送和 VRRP 抢 VIP 也一起被跳过了**，这比策略本身更严重。

修法：逐行判，并跳过"名字 + 数字"的计数行（末列纯数字 + 整行没有 CLI 错误行必有的
`<命令>: ` 前缀）。只看末列是数字会把 `set interface mtu host-eth3 1500` 这种回显也
当计数行，所以再加"没有冒号"；反过来 `ip route add: failed 999` 带前缀，仍会被认出。
回归测试 `TestVPPErrorIgnoresInterfaceCounters` 用 CPE2 那次实测的整段输出。

## 3. 三个测量陷阱（都曾把我带偏）

### 3.1 `ping` 不加 `-I` → 源地址是客户口地址

`ping 172.16.12.1` 从 cust3 发出，源地址是 cust3 的客户口 `172.31.3.2`，不是
site 环回。cust12 侧没有任何回 `172.31.3.0/24` 的路由，**请求到了、回复根本不会产生**，
表现却是"策略不通 100% 丢包"。

必须写 `ping -I 172.16.3.1 …`。这一条抓包才看清：

```
172.16.3.1 > 172.16.12.1: ICMP echo request
172.16.12.1 > 172.16.3.1: ICMP echo reply     ← 请求到的那一刻就回了
```

### 3.2 `show ip fib table N` 里第一个 `to:[…]` 是 `0.0.0.0/0` 的计数

彩表里既有兜底的 `0.0.0.0/0` 也有目标 `/32`。用 `awk '/to:\[/{print;exit}'` 取到的是
`/0` 那条的计数，于是"彩表从来没转发过"的结论是假的 —— 实际两张表各精确走了 5 个包
（5×84 字节）。要按前缀定位到那个块再取计数器。

### 3.3 在 CPE 自己的 shell 里 `ping -I <客户口地址>` 绕开了 ABF

本机发包从 lcp tap 进 VPP，走的是主表，**不经过客户口的 `ip4-unicast` 特征弧**，
所以 ABF 永远不匹配。当时看到 `ping -I 172.16.12.1 172.16.4.1` 通，就以为策略生效了，
其实是包漏到 WAN 默认路由被别处回了一下。策略只能由**客户路由器**发起的流量验证。

## 4. 双归站点的回程：策略是每台设备的

site12 是双归的，cust12 回包按流哈希到 CPE1 或 CPE2。只给 CPE1 配策略时，落到 CPE2
的回程在主表查不到 172.16.3.1/32，就顺着 `0.0.0.0/0` 漏进 WAN 了（客户口 rx +5、
无 drop、无 no-route，包是"正常转发"出去的）。

所以给 CPE2 补了对称的一行。这不是缺陷，是"策略按设备配"这个设计的必然结果：
**一个站点有几台盒子承载，就得在几台上都配**。真正的兜底应该是不配的那台至少把
overlay 前缀留在主表里（颜色 0 折叠），这属于动态策略那一轮的事。

## 5. 验证矩阵

| 场景 | 操作 | 期望 | 实测 |
|---|---|---|---|
| 下发面 | 发布 3 行 | ACL/ABF/挂口齐 | ACL 0/1/2 = `sr-pol-1/2/3`，policy 1001/1002/1003，挂 `host-enp0s8` |
| 端到端 | `cust12 -I 172.16.12.1 → 172.16.3.1` / `cust3 -I 172.16.3.1 → 172.16.12.1` | 通 | 5/5、0% 丢包，两个方向 |
| 幂等 | 同一份再发一次 | 零 churn | 控制台 `changed=False`；ACL 索引与 policy id 全不变，日志 `已存在且一致 … 不动` |
| 改前缀 | 行 2 的 `172.16.4.0/24` → `172.16.4.1/32` | ACL 原地替换 | `acl-index 1` 内容变成 /32，索引不变、策略不动 |
| 换颜色 | 行 2 色 3 → 色 2 | 删后重建 | policy 1002 的 deag 从 `fib-index:4`(3000) 变 `fib-index:3`(2000)，重新挂口 |
| 删行 | 删掉行 3 | 策略与 ACL 一并清 | policy 1003 与 `sr-pol-3`（索引 2）都消失，1001/1002 不受影响 |
| VPP 重启 | CPE3 `systemctl restart vpp` | 两半都重放 | +35 s 时彩表已重建（兜底 + `/32` 两条 MPLS 路径）、ACL/ABF 还空；+79 s 时 ACL `sr-pol-1`（**索引又是 0**）+ policy 1001 回来，挂口在；业务恢复 5/5 |

VPP 重启那次尤其有说服力：重放出来的第一张 ACL 又落在索引 0，走的正是 §2.1 那条
新路径 —— 换修复之前，这一次重放会直接以 `需要一个 ACL index` 失败。
